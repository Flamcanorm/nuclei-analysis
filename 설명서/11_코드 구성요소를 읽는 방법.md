# 코드 구성요소를 읽는 방법 #전지성

## 왜 이 문서가 필요한가?

코드에서 함수 하나의 내용만 읽으면 전체 역할을 놓치기 쉽다. Nuclei처럼 큰 프로그램은 선언 파일, 생성 함수, 호출 함수, 인터페이스 구현이 여러 폴더에 나뉜다.

예를 들어 `Runner`를 이해하려면 다음을 모두 봐야 한다.

```text
internal/runner/runner.go의 Runner 구조체 선언
→ 같은 파일의 New 함수
→ cmd/nuclei/main.go의 runner.New 호출
→ RunEnumeration 메서드
→ pkg/core의 Engine 호출
→ Close 메서드의 자원 정리
```

## 선언, 초기화, 사용의 차이

### 선언

이름과 형태를 프로그램에 알려준다.

```go
type Runner struct {
    options *types.Options
}
```

이 코드는 Runner가 `options` 필드를 가진다고 정의하지만 실제 Runner 객체를 만들지는 않는다.

### 초기화 또는 생성

실제 값을 가진 객체를 만든다.

```go
runner := &Runner{
    options: options,
}
```

### 사용

만든 객체의 필드나 메서드를 이용한다.

```go
nucleiRunner.RunEnumeration()
```

세 단계를 섞지 않고 구분하면 “구조체가 존재한다”와 “이번 실행에서 실제 객체가 만들어졌다”를 혼동하지 않게 된다.

## 변수의 범위별 역할

### 전역 또는 패키지 변수

파일의 여러 함수가 공유한다. `main.go`의 `options`가 예다. 접근은 편하지만 변경 위치가 많아질 수 있다.

### 지역변수

함수 실행 동안만 사용한다. `nucleiRunner`, `executorEngine`, `loaderConfig`, `store`가 예다. 사용 범위가 좁아 추적하기 쉽다.

### 구조체 필드

객체의 생명주기 동안 상태를 보관한다. `Runner.output`, `Runner.catalog` 등이 예다. 여러 메서드가 같은 객체를 공유할 수 있다.

## 함수 종류를 구분하는 방법

### 일반 함수

```go
func New(options *types.Options) (*Runner, error)
```

특정 객체가 없어도 패키지 이름으로 호출한다. `runner.New(options)`처럼 사용한다.

### 메서드

```go
func (r *Runner) RunEnumeration() error
```

`r *Runner`가 Receiver다. 특정 Runner 객체에 연결되어 `r.options`, `r.output` 같은 필드를 사용할 수 있다.

### Callback

나중에 특정 사건이 발생했을 때 호출하도록 함수 자체를 값으로 전달한다.

```go
Callback func(*output.ResultEvent)
```

Engine은 누가 결과를 받을지 구체적으로 알 필요 없이 Callback이 있으면 호출한다.

## 구조체를 읽는 순서

1. 구조체가 선언된 파일을 찾는다.
2. 필드를 역할별로 묶는다.
3. `New...` 생성 함수를 찾는다.
4. 생성 함수의 호출자를 찾는다.
5. 필드가 대입되는 위치를 찾는다.
6. 구조체의 메서드를 찾는다.
7. `Close`, `Purge` 같은 종료 함수를 찾는다.

## 인터페이스를 읽는 순서

인터페이스는 “무엇을 할 수 있어야 하는가”를 선언하고, 구현체는 “그 작업을 어떻게 하는가”를 정의한다.

```text
catalog.Catalog 인터페이스
├─ OpenFile
├─ GetTemplatePath
├─ GetTemplatesPath
└─ ResolvePath

disk.DiskCatalog 구현체
└─ 위 메서드를 디스크와 fs.FS 방식으로 구현
```

인터페이스를 보면 다음 세 가지를 찾아야 한다.

1. 인터페이스 선언 파일
2. 실제 구현 구조체
3. 구현체를 만들어 인터페이스 변수에 넣는 위치

Nuclei의 경우 `runner.catalog` 필드 타입은 `catalog.Catalog`이고, `disk.NewCatalog()`의 반환값을 대입한다.

## 연결을 찾을 때 검색할 문자열

| 알고 싶은 것 | 검색 예 |
|---|---|
| 구조체 선언 | `type Runner struct` |
| 생성 함수 | `func New(`, `NewRunner`, `NewCatalog` |
| 함수 호출 | `runner.New(` |
| 필드 대입 | `runner.catalog =` |
| 메서드 | `func (r *Runner)` |
| 인터페이스 선언 | `type Writer interface` |
| 옵션 등록 | `&options.Debug` |
| 옵션 사용 | `options.Debug`, `r.options.Debug` |

## 설계 이유를 쓸 때 사실과 추론을 구분하는 방법

### 코드에서 직접 확인되는 사실

- Runner 구조체에 `output output.Writer` 필드가 있다.
- `New()`이 `output.NewStandardWriter(options)`를 호출한다.
- `RunEnumeration()`이 같은 `r.output`을 ExecutorOptions에 넣는다.
- `Close()`가 Writer를 닫는다.

### 사실에서 도출한 설계 해석

> Writer를 Runner에 보관하는 것은 생성, 공유, 종료의 책임을 한 생명주기에 묶고 여러 실행 단계가 같은 결과 카운터와 출력 파일을 사용하게 하려는 구조로 해석할 수 있다.

설계자의 생각을 직접 적은 주석이나 문서가 없다면 “반드시 이 목적이다”가 아니라 “이런 효과가 있으며, 이 구조로 해석할 수 있다”고 써야 정확하다.

## 좋은 분석 문단의 형식

```text
[선언]
pkg/core/engine.go에 Engine 구조체가 선언되어 있다.

[생성]
Runner.RunEnumeration()이 core.New(r.options)으로 Engine을 만든다.

[연결]
SetExecuterOptions(executorOpts)로 Writer, Catalog, RateLimiter 등을 전달한다.

[사용]
ExecuteScanWithOpts()가 Template 목록과 InputProvider를 받아 실행한다.

[설계 이유]
Engine은 CLI 파싱과 파일 생성 방법을 몰라도 되고, 준비된 실행 의존성만 사용한다.

[주의]
SetExecuterOptions 호출이 빠지면 Engine에 실행 환경이 연결되지 않는다.
```

앞으로 각 분석 파일도 이 형식을 사용하면 문서 간 상세도 차이를 줄일 수 있다.
