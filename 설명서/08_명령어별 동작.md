# 명령어별 동작 설명서 #전지성


[[07_전체 스캔 실행 흐름]]에서 모든 명령이 `readConfig()`의 Parse를 거쳐 Options가 된다고 설명했다. 이 문서는 각 명령이 **어느 Options 필드를 바꾸고, 어느 파일의 조건문이 읽고, 전체 흐름의 어느 부분을 바꾸는지** 연결한다.

## 명령을 분석할 때 보는 네 단계

```text
터미널 옵션 이름
  ↓ cmd/nuclei/main.go의 readConfig 등록
Options 구조체 필드
  ↓ main 또는 Runner의 조건문
선택된 실행 경로
  ↓
화면·파일 결과
```

| 명령 | 연결되는 대표 필드 | 값을 주로 사용하는 위치 | 바뀌는 단계 |
|---|---|---|---|
| `-debug` | `Options.Debug` | `runner.ParseOptions`, Writer·Interactsh 설정 | 로그와 요청·응답 표시 |
| `-tl` | `Options.TemplateList` | `Runner.RunEnumeration()` | 전체 Compile 대신 Metadata 목록 출력 후 종료 |
| `-tgl` | `Options.TagList` | `Runner.RunEnumeration()` | Tag 목록만 로드하고 종료 |
| `-tags` | `Options.Tags` | `loader.NewConfig`, Store Filter | Loader가 남기는 Template 변경 |
| `-o` | `Options.Output` | `output.NewStandardWriter` | Writer의 파일 목적지 추가 |
| `-json-export` | `Options.JSONExport` | `internal/runner/options.go`의 Reporting 설정 | ResultEvent를 JSON 파일로 모아 저장 |
| `-omit-raw` | `Options.OmitRawRequests` | Reporting·JSON·Markdown·PDF Exporter 설정 | 요청·응답 원문 필드 제외 |
| `-ldf` | `Options.ListDslSignatures` | `main()`의 조기 종료 조건 | Runner 생성 전에 DSL 목록 출력 |

여기서 “대표 필드”라고 쓴 이유는 출력 옵션처럼 하나의 명령이 Reporting Options 등 다른 구조체로 다시 복사될 수 있기 때문이다.

## 명령 표기 주의

터미널에는 Markdown 링크 문법을 넣지 않는다.

```bash
./nuclei -u https://example.com
```

다음 표기는 문서에서 클릭 가능한 링크를 만드는 Markdown 문법이므로 터미널 명령이 아니다.

```text
[https://example.com/](https://example.com/)
```

## -debug
<!-- main-line-section-tags: #L69 #L168 #L237 -->
#L69 #L168 #L237

```bash
./nuclei -u https://example.com -debug
```

전송 요청과 수신 응답을 자세히 표시해 템플릿이 왜 매칭되거나 실패했는지 확인한다. 탐지 수 자체를 늘리는 필터가 아니라 관찰 가능한 정보를 늘리는 옵션이다.

앞의 전체 흐름에서 Template 선택이나 Engine 반복 순서를 바꾸는 것이 아니라, `Options.Debug`가 Runner의 Interactsh 설정과 Output Writer의 디버그 출력 설정으로 전달되어 보이는 정보를 늘린다.

## -tl
<!-- main-line-section-tags: #L69 #L237 -->
#L69 #L237

```bash
./nuclei -tl
```

`template-list` 성격의 명령으로, 현재 옵션과 필터 조건을 통과해 로드될 템플릿 목록을 보여준다. 대상을 실제로 스캔한 탐지 결과와는 다르다.

`./nuclei -u https://example.com -o result.txt`의 결과는 실제 스캔 매칭 결과이므로 `-tl` 보고서의 출력으로 사용하면 안 된다.

`RunEnumeration()`은 `TemplateList`가 true이면 `store.LoadTemplatesOnlyMetadata()`를 사용한다. 여기서 Metadata는 ID, Info, 경로처럼 목록 표시에 필요한 정보이며, 일반 스캔처럼 모든 요청을 Compile하고 Engine에 넘기지 않는다.

## -tgl
<!-- main-line-section-tags: #L69 #L237 -->
#L69 #L237

```bash
./nuclei -tgl
```

`tgl`은 **Tag List**이며, 현재 설치된 템플릿에서 사용할 수 있는 태그 목록을 출력한다. `main.go`에는 다음처럼 등록되어 있다.

```go
flagSet.BoolVar(
    &options.TagList,
    "tgl",
    false,
    "list all available tags",
)
```

`-tl`은 현재 필터와 일치하는 **템플릿 목록**, `-tgl`은 사용 가능한 **태그 목록**이다.

```text
-tl  → 어떤 템플릿 파일들이 선택되는가?
-tgl → 템플릿 분류에 어떤 태그들이 존재하는가?
```

따라서 `-tgl`의 정상 출력은 `cve`, `exposure`, `tech` 같은 태그 이름과 관련된 목록이어야 한다. 입력이 `-tgl`인데 `[dns-waf-detect:cloudflare] ... example.com` 같은 대상 탐지 결과가 나온 것으로 보고서를 작성하면, 다른 스캔의 출력을 붙인 것이다. `-tgl`은 대상 URL을 검사하는 명령이 아니다.

버전이 바뀌었을 때는 다음 도움말로 현재 정의를 다시 확인하는 것이 안전하다.

```bash
./nuclei -h
```

## -tags
<!-- main-line-section-tags: #L69 #L237 -->
#L69 #L237

```bash
./nuclei -u https://example.com -tags cve
```

템플릿의 `info.tags`에 `cve`가 있는 템플릿만 선택한다. 결과가 없다는 것은 Nuclei가 실패했다는 뜻이 아니라, 선택된 템플릿이 대상에서 매칭되지 않았다는 뜻일 수 있다.

```bash
./nuclei -tl -tags exposure
```

스캔 전에 exposure 태그 필터를 통과하는 템플릿 목록을 확인할 수 있다.

연결은 `-tags` → `Options.Tags` → `loader.NewConfig()`의 `Config.Tags` → Store의 Metadata Filter 순서다. 즉 Engine이 실행 중 태그를 검사하는 것이 아니라, Engine에 전달하기 전 Loader가 템플릿을 줄인다.

## -o
<!-- main-line-section-tags: #L69 #L237 -->
#L69 #L237

```bash
./nuclei -u https://example.com -o result.txt
```

탐지 결과를 일반 텍스트 파일에 저장한다. 터미널에는 버전, 로드 수, 진행률 같은 Logger 메시지도 보일 수 있지만 `result.txt`는 기본적으로 결과 Writer가 처리한 탐지 결과 중심이다.

앞 문서의 `output.Writer` 연결에서 설명했듯 `output.NewStandardWriter(options)`가 `Options.Output` 경로를 읽어 파일을 열고, 이후 Engine과 프로토콜 계층에서 같은 Writer 참조를 사용한다.

## -json-export
<!-- main-line-section-tags: #L69 #L237 -->
#L69 #L237

```bash
./nuclei -u https://example.com -json-export result.json
```

탐지 결과를 JSON 형식으로 저장한다. 사람이 읽는 한 줄 출력보다 다른 프로그램이 필드를 안정적으로 읽기 쉽다.

활용 예:

- 결과를 웹 대시보드에 넣기
- 취약점 관리 시스템으로 전송
- 템플릿 ID와 심각도별 통계 계산
- 자동화 스크립트에서 필드 추출
- 데이터베이스에 구조화해 저장

코드 연결은 다음과 같다.

```text
-json-export result.json
  ↓ readConfig의 StringVarP
Options.JSONExport = "result.json"
  ↓ internal/runner/options.go
jsonexporter.Options{File: options.JSONExport, ...}
  ↓ reporting.New가 JSON Exporter 생성
ResultEvent들을 메모리에 모음
  ↓ Exporter.Close()
지정한 JSON 파일에 최종 배열 기록
```

여기서 `jsonexporter.Options`는 전체 실행 설정인 `types.Options`와 다른 구조체다. JSON Exporter가 필요한 파일 경로와 raw 생략 여부만 담는다.

## -omit-raw
<!-- main-line-section-tags: #L69 #L237 -->
#L69 #L237

JSON 계열 결과에서 원본 요청과 응답의 raw 내용을 생략한다. raw는 헤더와 본문 등을 포함한 원문 데이터다.

사용 이유:

- 결과 파일 크기 감소
- 인증 토큰이나 응답 본문의 민감정보 노출 범위 감소
- 분석에 필요한 요약 필드만 보관

단, 나중에 요청·응답을 재검토해야 한다면 raw가 없어서 근거가 부족할 수 있다.

코드에서는 `-omit-raw`가 `Options.OmitRawRequests`에 저장된다. `internal/runner/options.go`가 이 값을 JSON, JSONL, Markdown, PDF 등의 각 Exporter Options에 `OmitRaw`라는 필드명으로 다시 복사한다.

```text
Options.OmitRawRequests
  ↓ 출력 형식별 설정으로 복사
jsonexporter.Options.OmitRaw
jsonl.Options.OmitRaw
markdown.Options.OmitRaw
pdf.Options.OmitRaw
  ↓
Exporter가 ResultEvent의 Request·Response 원문을 제외
```

앞의 [[09_용어 사전]]에서 설명한 것처럼 이 raw는 네트워크 요청·응답 원문이다. Parser Cache의 템플릿 YAML·JSON 원문과는 다른 데이터다.

## -list-dsl-function / -ldf
<!-- main-line-section-tags: #L74 #main/L74/dsl -->
#L74 #main/L74/dsl

```bash
./nuclei -ldf
```

템플릿 DSL에서 사용할 수 있는 함수 서명을 출력하고 스캔 없이 종료한다. 자세한 코드 흐름은 [[06_템플릿과 DSL]]을 참고한다.

이 명령은 다른 목록 명령과 종료 위치가 다르다. `main()`이 `readConfig()` 직후 필드를 검사하므로 `runner.New()`조차 호출하지 않는다. 반면 `-tl`과 `-tgl`은 Loader가 필요하므로 Runner 생성 후 `RunEnumeration()` 안에서 종료된다.

다음 [[09_용어 사전]]은 이 문서들에서 반복된 이름을 짧게 다시 찾는 색인이다.

## -verbose와 -vv
<!-- main-line-section-tags: #L69 #L168 #L237 -->
#L69 #L168 #L237

- `-v`: 기본보다 자세한 실행 정보 표시
- `-vv`: 로드된 템플릿을 확인하는 데 쓰는 더 상세한 출력

이 옵션은 필터 결과를 검증할 때 유용하지만, 어떤 템플릿이 매칭될지를 보장하지는 않는다.

## 명령과 결과를 보고서에 넣을 때의 원칙

1. 입력 명령을 실제 터미널 문법으로 적는다.
2. 해당 명령을 실행했을 때 나온 출력만 붙인다.
3. 템플릿 목록과 탐지 결과를 구분한다.
4. `[INF]` 상태 메시지와 탐지 결과를 구분한다.
5. Nuclei 및 templates 버전을 기록한다.
6. 외부 상태에 따라 순서나 값이 바뀔 수 있음을 적는다.
