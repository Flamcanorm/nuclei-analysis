# 내부 패키지 설명서 #전지성

## 내부 패키지란?

이 분석 저장소에서 내부 패키지는 Nuclei 프로젝트 안에서 프로그램의 핵심 동작을 구현한 코드를 뜻한다. 사용자가 직접 호출하기보다는 `main()`과 Runner가 조립해 사용한다.

## Options — 실행 설정 보관함

관련 문서: `02_Internal_Packages/pkg_types.md`

`pkg/types/types.go`의 `Options`는 프로그램 전체 설정을 한 구조체에 모은다.

```text
Options
├─ 대상: Targets, TargetsFilePath
├─ 템플릿: Templates, Workflows, Tags
├─ 출력: Output, JSONExport, OmitRaw
├─ 로그: Debug, Verbose, Silent, Logger
├─ 성능: RateLimit, BulkSize, TemplateThreads
└─ 기타: Headless, Interactsh, Cloud 등
```

Options 자체가 스캔하는 것은 아니다. 다른 구성요소가 “이번 실행에서 무엇을 해야 하는가”를 알 수 있도록 값을 제공한다.

### 선언과 생성

- 구조체 선언: `pkg/types/types.go`의 `type Options struct`
- CLI 전역 객체 생성: `cmd/nuclei/main.go`의 `options = &types.Options{}`
- 값 입력: `readConfig()`의 goflags 등록과 `flagSet.Parse()`
- 값 보정: `runner.ParseOptions(options)`
- 첫 주요 소비자: `runner.New(options)`

`Options` 필드는 수가 매우 많다. 하나의 거대한 설정 구조체는 전달은 편하지만 서로 관련 없는 구성요소가 모든 설정을 볼 수 있다는 단점도 있다. 실제 실행 단계에서는 이 문제를 줄이기 위해 Loader용 `loader.Config`, 프로토콜용 `ExecutorOptions`처럼 목적별 구조체를 다시 만든다.

## runner/options.go — 옵션 규칙과 검증

관련 문서: `02_Internal_Packages/runner_options.md`

이 파일은 CLI 옵션 등록 파일인 `main.go`와 역할이 다르다.

- `main.go/readConfig`: 옵션의 이름, 별칭, 기본값, 도움말을 등록하고 파싱
- `runner/options.go`: 파싱된 값이 유효한지 검사하고 실행에 맞게 보정

`ConfigureOptions()`는 goflags가 YAML·JSON 템플릿 경로를 단순 목록 파일로 잘못 펼치지 않도록 `IsFromFile` 규칙을 설정한다.

## Runner — 구성요소 준비와 연결

관련 문서: `02_Internal_Packages/runner_runner.md`

Runner는 다음 구성요소를 준비하고 연결하는 상위 실행 관리자다.

- Catalog와 Template Loader
- Template Parser
- InputProvider
- Output Writer
- Progress 통계
- Interactsh Client
- RateLimiter
- Engine 실행에 필요한 옵션

“스캔 전체를 지휘한다”는 말은 Runner가 모든 패킷을 직접 만든다는 뜻이 아니다. 각 담당 객체를 생성하고 올바른 순서로 호출한다는 뜻이다.

### Runner 구조체 선언

`internal/runner/runner.go`에는 다음 종류의 필드가 선언되어 있다.

| 필드 | 실제 타입 | 연결 대상 |
|---|---|---|
| `options` | `*types.Options` | 전체 실행 설정 |
| `catalog` | `catalog.Catalog` | 템플릿 파일 접근 |
| `parser` | `parser.Parser` | YAML·JSON 해석과 Cache |
| `inputProvider` | `provider.InputProvider` | 스캔 대상 공급 |
| `output` | `output.Writer` | 결과 기록 |
| `rateLimiter` | `*ratelimit.Limiter` | 요청 속도 제한 |
| `interactsh` | `*interactsh.Client` | OAST 상호작용 |
| `browser` | `*engine.Browser` | Headless 실행 |
| `progress` | `progress.Progress` | 진행률 집계 |
| `Logger` | `*gologger.Logger` | 상태 로그 |

Runner 필드는 구성요소를 **소유한다기보다 실행 동안 참조를 보관**한다. `Close()`가 이 필드를 이용해 Writer, InputProvider, Browser, 임시 디렉터리 등을 정리하므로 생성부터 종료까지 같은 객체가 유지된다.

### New(options)

전달받은 Options를 바탕으로 현재 실행에 필요한 객체를 만든다. Headless가 꺼져 있으면 Browser가 필요 없고, 결과 파일 옵션에 따라 Writer 설정도 달라진다.

실제 생성 관계는 다음과 같다.

```text
runner.New(options)
├─ templates.NewParser() → runner.parser
├─ engine.New(options) → runner.browser         [Headless일 때만]
├─ disk.NewCatalog(...) → runner.catalog
├─ provider.NewInputProvider(...) → runner.inputProvider
├─ output.NewStandardWriter(options) → runner.output
├─ progress.NewStatsTicker(...) → runner.progress
├─ interactsh.New(opts) → runner.interactsh
└─ utils.GetRateLimiter(...) → runner.rateLimiter
```

각 생성 함수가 실패할 수 있으므로 `New()`은 `(*Runner, error)`를 반환한다. 중간에 실패하면 `cleanupOnError`와 `defer`가 임시 디렉터리를 정리하고, 성공하면 `cleanupOnError = false`로 바꿔 이후 `Runner.Close()`가 정리하도록 책임을 넘긴다.

### 왜 모든 객체를 Runner 구조체에 넣는가?

실행 중 여러 단계가 같은 Writer, Parser, RateLimiter를 사용해야 하기 때문이다. 함수마다 새 객체를 만들면 다음 문제가 생긴다.

- 결과 수가 Writer마다 따로 계산됨
- RateLimiter가 공유되지 않아 전체 속도 제한이 깨짐
- Parser Cache가 재사용되지 않음
- 종료 시 어떤 객체를 닫아야 하는지 추적하기 어려움

Runner에 참조를 모으면 생성·공유·종료의 생명주기를 한곳에서 관리할 수 있다.

### RunEnumeration()

템플릿을 로드하고 입력 대상을 받아 Engine 실행으로 넘긴다. 스캔 완료 후 통계와 정리 작업도 연결한다.

`RunEnumeration()`에서 가장 중요한 중간 구조체는 `protocols.ExecutorOptions`다.

```go
executorOpts := &protocols.ExecutorOptions{
    Output:      r.output,
    Options:     r.options,
    Progress:    r.progress,
    Catalog:     r.catalog,
    RateLimiter: r.rateLimiter,
    Interactsh:  r.interactsh,
    Browser:     r.browser,
    Parser:      r.parser,
    Logger:      r.Logger,
    ...
}
```

Runner가 가진 필드를 실행기가 받을 묶음으로 다시 조립한다. 이것이 Runner가 구성요소를 “연결한다”는 표현의 가장 직접적인 코드 근거다.

### Options와 ExecutorOptions의 차이

| 구조체 | 질문 | 내용 |
|---|---|---|
| `types.Options` | 사용자가 무엇을 요청했는가? | Target, Tags, Debug, 동시성, 출력 경로 등 설정값 |
| `protocols.ExecutorOptions` | 요청 실행기가 무엇을 사용할 수 있는가? | Writer, Catalog, Parser, RateLimiter, Browser 등 준비된 객체와 현재 템플릿 정보 |

`Options`만 전달하면 각 프로토콜 실행기가 Writer와 RateLimiter를 다시 만들어야 한다. `ExecutorOptions`는 이미 생성된 공통 객체를 의존성으로 전달해 같은 자원을 공유하게 한다.

## Catalog — 템플릿 파일 위치 관리자

관련 문서: `catalog_disk.md`, `catalog_loader.md`

Catalog는 템플릿의 **내용을 판단하는 객체가 아니라 파일을 찾고 여는 통로**다.

### DiskCatalog

- 템플릿 기본 디렉터리 계산
- 상대 경로와 절대 경로 처리
- 파일이나 URL 열기
- glob 패턴과 디렉터리에서 템플릿 경로 찾기

`catalog.Catalog`는 `OpenFile`, `GetTemplatePath`, `GetTemplatesPath`, `ResolvePath`를 요구하는 인터페이스이고, `disk.DiskCatalog`가 이를 실제 디스크 또는 `fs.FS` 방식으로 구현한다.

Runner 필드 타입이 구체적인 `*disk.DiskCatalog`가 아니라 `catalog.Catalog`인 이유는 Loader와 Parser가 저장 방식보다 “파일을 열고 경로를 해결할 수 있는가”에만 의존하게 하기 위해서다. 실제 디스크 대신 임베디드 파일시스템이나 테스트용 구현을 넣기 쉬워진다.

### Loader

Catalog가 찾은 후보 중 실제로 사용할 템플릿을 선택한다.

- YAML·JSON 템플릿 파싱
- tags, severity, author, id 필터 적용
- 템플릿과 Workflow 구분
- 중복과 제외 조건 처리
- 로드 결과를 Engine이 쓸 목록으로 제공

Loader에는 두 구조체가 있다.

```text
loader.Config
└─ 템플릿 경로, tags, severity, Catalog, ExecutorOptions 등 입력 조건

loader.Store
└─ 필터를 통과해 로드된 templates와 workflows 및 Cache·Index
```

`loader.NewConfig(r.options, r.catalog, executorOpts)`가 거대한 Options에서 Loader가 필요한 필드만 복사하고, `loader.New(loaderConfig)`가 Store를 만든다. 이후 `store.Load()`가 실제 목록을 채우고 `store.Templates()`가 Engine에 전달할 Template 객체를 반환한다.

이 분리는 “설정”과 “실행 결과로 쌓인 상태”를 구분한다. Config는 입력 조건이고 Store는 그 조건을 적용한 결과다.

```text
Catalog: 파일이 어디 있는가?
Loader: 그 파일을 이번 실행에 사용할 것인가?
Parser: 파일 내용이 어떤 Template 객체인가?
```

## Parser — 템플릿 원문을 객체로 해석

Parser는 YAML 또는 JSON 글자를 `Template` 구조체의 필드로 변환한다.

```text
YAML·JSON 원문
  ↓ Parser
Template 객체
├─ ID
├─ Info
├─ HTTP·DNS·SSL 요청 정의
├─ Matchers
└─ Extractors
```

같은 템플릿을 반복해서 읽고 해석하는 비용을 줄이기 위해 Cache를 사용할 수 있다. Cache는 이전에 만든 Template 객체를 메모리에 잠시 보관하는 저장소다.

### Parser 구조체

`pkg/templates/parser.go`:

```text
Parser
├─ ShouldValidate
├─ NoStrictSyntax
├─ parsedTemplatesCache
├─ compiledTemplatesCache
└─ Mutex
```

- Parsed Cache: 필터와 검증에 사용할 가벼운 Template 객체
- Compiled Cache: 프로토콜 실행기까지 준비된 무거운 Template 객체
- Mutex: 여러 템플릿을 동시에 처리할 때 Cache 상태 충돌 방지

### ParseTemplate의 실제 연결

```text
ParseTemplate(templatePath, catalog)
  ↓ Cache.Has(templatePath)
이미 있으면 Template 재사용
  ↓ 없으면
Catalog를 이용해 Reader 열기
  ↓
확장자로 JSON 또는 YAML 판별
  ↓
Template 구조체로 Unmarshal
  ↓
StoreWithoutRaw로 Parsed Cache 저장
  ↓
*Template 반환
```

### StoreWithoutRaw를 쓰는 이유

Parsed Cache는 해석된 Template 객체가 있으면 필터와 검증을 수행할 수 있다. YAML·JSON 원문 문자열까지 함께 보관하면 같은 내용이 원문과 객체 두 형태로 메모리에 남는다. 그래서 `StoreWithoutRaw(templatePath, template, nil)`은 `raw` 필드를 빈 문자열로 두어 중복 보관을 피한다.

이 선택은 무조건 메모리를 가장 적게 쓴다는 뜻은 아니다. Template 객체와 Cache 자체는 여전히 메모리를 쓴다. 정확한 표현은 **재파싱 비용을 줄이기 위해 객체를 메모리에 보관하되, 불필요한 원문 중복은 줄이는 절충**이다.

## Engine — 실제 실행 조합

관련 문서: `02_Internal_Packages/core_engine.md`

Engine은 Loader가 넘긴 템플릿과 InputProvider가 넘긴 대상을 조합해 실행한다.

```text
대상 1개 × 템플릿 여러 개
또는
템플릿 1개 × 대상 여러 개
```

주요 책임은 다음과 같다.

- 선택된 ScanStrategy에 맞는 실행 순서 결정
- WorkPool을 이용한 동시 실행
- 프로토콜 요청 실행
- 결과 이벤트를 Callback과 Writer로 전달
- 오류와 진행률 처리

### Engine 구조체와 연결

`pkg/core/engine.go`:

```go
type Engine struct {
    workPool     *WorkPool
    options      *types.Options
    executerOpts *protocols.ExecutorOptions
    Callback     func(*output.ResultEvent)
    Logger       *gologger.Logger
}
```

| 필드 | 이유 |
|---|---|
| `workPool` | 동시 실행 작업 수 관리 |
| `options` | ScanStrategy와 동시성 등 사용자 설정 확인 |
| `executerOpts` | 프로토콜 실행에 필요한 공통 객체 전달 |
| `Callback` | 결과가 생겼을 때 호출할 후속 처리 연결 |
| `Logger` | 실행 상태와 오류 기록 |

Runner는 `core.New(r.options)`으로 Engine을 만든 뒤 `SetExecuterOptions(executorOpts)`를 반드시 호출한다. Engine의 생성 시점에는 설정으로 WorkPool을 만들고, 두 번째 단계에서 Runner가 준비한 실행 의존성을 붙인다.

이 두 단계 설계는 Engine 생성과 실행 환경 연결을 분리하지만, `SetExecuterOptions` 호출을 빠뜨릴 위험도 있다. 실제 주석도 실행 전에 필수라고 명시한다.

### 최종 호출

```go
engine.ExecuteScanWithOpts(
    context.Background(),
    finalTemplates,
    r.inputProvider,
    r.options.DisableClustering,
)
```

여기서 Engine이 받는 것은 Template 객체 목록, InputProvider, Clustering 사용 여부다. Writer와 RateLimiter는 앞서 `SetExecuterOptions()`로 이미 연결되었다.

## ScanStrategy — 반복 순서

관련 문서: `02_Internal_Packages/types_scanstrategy.md`

대표적인 전략은 두 관점으로 이해할 수 있다.

- Template 중심: 템플릿 하나를 여러 대상에 적용한 뒤 다음 템플릿으로 이동
- Host 중심: 대상 하나에 여러 템플릿을 적용한 뒤 다음 대상으로 이동

최종 탐지 의미는 같아도 메모리 사용, 연결 재사용, 진행 순서가 달라질 수 있다.

## InputProvider — 대상 공급자

InputProvider는 `-u`, `-l`, 표준 입력 등 여러 입력 경로를 하나의 대상 공급 방식으로 정리한다.

```text
-u https://example.com
-l targets.txt
파이프로 전달된 표준 입력
        ↓
InputProvider
        ↓
Engine이 하나씩 받을 수 있는 대상
```

`provider.InputProvider`는 `Count`, `Iterate`, `Set`, `SetWithExclusions`, `Close` 등을 요구하는 인터페이스다. 단순 URL 목록, OpenAPI, Burp 요청처럼 입력 형식은 달라도 Engine은 `Iterate()`로 대상을 받을 수 있다.

왜 인터페이스로 분리했는가? Engine이 입력 파일의 형식별 파싱 방법까지 알게 되면 실행 코드가 복잡해진다. InputProvider가 형식 차이를 숨기면 Engine은 모든 입력을 `MetaInput` 흐름으로 처리한다.

## Output Writer — 탐지 결과 전달자

Writer는 Engine에서 나온 `ResultEvent`를 화면이나 파일로 직렬화해 보낸다.

- 일반 터미널 결과
- `-o` 텍스트 파일
- JSON/JSONL 결과
- Markdown·SARIF 등 지원 형식
- Cloud 전송 Writer

Writer가 `[INF]` 상태 로그까지 모두 쓰는 것은 아니다. 상태 로그는 Logger가 담당하고, Writer는 주로 탐지 결과를 담당한다.

`output.Writer` 인터페이스는 `Write(*ResultEvent)`, `WriteFailure`, `Request`, `ResultCount`, `Close` 등을 요구한다. 기본 구현은 `StandardWriter`이고, Cloud나 통계 Writer를 `MultiWriter`로 함께 묶을 수 있다.

Runner 필드가 `*StandardWriter`가 아닌 `output.Writer`인 이유는 한 실행에서 출력 목적지를 교체하거나 여러 Writer를 합칠 수 있게 하기 위해서다.

```text
ResultEvent
  ↓ output.Writer 인터페이스
  ├─ StandardWriter → 화면·텍스트 파일
  ├─ TrackerWriter → 통계
  └─ PDCP Writer → Cloud
```

## RateLimiter — 요청 속도 조절기

RateLimiter는 일정 시간 안에 보낼 수 있는 요청 수를 제한한다. 동시성 제한과 비슷해 보이지만 같은 개념은 아니다.

- 동시성: 한 시점에 몇 작업을 동시에 실행할지
- Rate Limit: 1초 또는 1분 동안 총 몇 요청을 허용할지

둘을 함께 사용해 로컬 자원과 대상 서버의 부하를 관리한다.

## pdcp/writer.go

관련 문서: `02_Internal_Packages/pdcp_writer.md`

일반 로컬 파일 Writer가 아니라 ProjectDiscovery Cloud로 결과를 보내는 경로와 관련된다. Team ID나 API 인증 정보를 확인하고 결과를 Cloud 자산과 연결할 수 있다.

## uncover/uncover.go

관련 문서: `02_Internal_Packages/uncover_uncover.md`

Uncover는 외부 인터넷 검색 서비스가 지원하는 엔진 정보를 제공하고, 해당 서비스를 통해 얻은 호스트를 Nuclei 입력 대상으로 연결한다. Nuclei가 무작위로 모든 인터넷 주소를 검사하는 기능은 아니다.
