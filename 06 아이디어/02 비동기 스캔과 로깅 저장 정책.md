# 비동기 스캔과 로깅 저장 정책

## 환경과 목표

- 운영 환경: Raspberry Pi OS, Linux
- 구현 언어: Python
- API: FastAPI
- 사용 가능한 저장공간: 약 50GB
- 목표: 네트워크 스캔 효율을 유지하면서 저장공간 고갈과 불필요한 쓰기를 방지한다.

## 최종 권장안

- 네트워크 스캔은 비동기로 구현한다.
- 동시에 실행하는 스캔은 기본 1개로 제한한다.
- 요청은 제한된 수의 worker가 generator에서 하나씩 가져간다.
- 운영 로그는 별도 파일을 만들지 않고 `systemd-journald`에 보낸다.
- 스캔 결과는 SQLite에 구조화해서 저장한다.
- 전체 요청·응답은 기본적으로 저장하지 않는다.
- 취약점이 탐지된 경우에만 크기가 제한된 증거를 저장한다.

## 비동기 스캔 구조

```text
FastAPI
  -> 작업 등록
      -> 제한된 Scan Queue
          -> ScanRunner 1개
              -> 최대 N개의 protocol worker
                  -> Matcher
                      -> Result writer queue
```

### 초기 설정 권장값

| 설정 | 초기값 |
|---|---:|
| 동시 실행 스캔 | 1개 |
| HTTP 동시 연결 | 20개 |
| 초당 요청 수 | 10 req/s |
| API 작업 대기열 | 최대 100개 |
| 프로토콜 내부 대기열 | 최대 500개 |
| 연결 timeout | 5초 |
| 읽기 timeout | 10초 |
| 전체 요청 timeout | 15초 |
| 최대 응답 본문 | 512KB |
| 재시도 | 1회 |

Raspberry Pi 모델, 메모리와 네트워크 상태를 측정한 후 HTTP 동시 연결을 20에서 50 정도까지 단계적으로 조절한다.

## 비동기와 동기를 나누는 기준

### 비동기로 구현할 부분

- HTTP/HTTPS 요청
- DNS 요청
- TCP/UDP/TLS 통신
- 작업 queue
- scan 취소 및 timeout
- 결과 writer queue

### 일반 동기 함수로 충분한 부분

- YAML 문서 한 개 파싱
- 짧은 정규식 matcher
- status, word, size 비교
- 결과 모델 변환
- 작은 JSON 문서 추출

### 별도 thread 또는 process가 필요한 부분

- Scapy/raw packet
- 무거운 정규식 또는 CPU 집약형 분석
- headless browser
- 동기 방식만 지원하는 외부 라이브러리

이 작업들을 FastAPI event loop에서 직접 실행하지 않는다.

## 메모리를 제한하는 실행 방식

payload가 10만 개라고 해서 10만 개의 asyncio Task를 생성하면 안 된다.

1. PayloadGenerator가 값 하나를 `yield`한다.
2. bounded queue에 제한된 수만 적재한다.
3. worker 20개가 하나씩 가져간다.
4. 완료한 항목은 즉시 메모리에서 제거한다.
5. response body도 지정한 최대 크기까지만 읽는다.

`TaskGroup`만 사용한다고 자동으로 메모리가 제한되는 것은 아니다. 생성하는 Task 수 자체를 queue 또는 Semaphore로 제한해야 한다.

## FastAPI BackgroundTasks 사용 여부

긴 스캔 작업을 `BackgroundTasks`에 직접 넣는 것은 권장하지 않는다.

MVP에서는 다음 구성이 가능하다.

- Uvicorn worker 1개
- 앱 lifespan에서 ScanRunner 1개 시작
- bounded `asyncio.Queue`
- SQLite에 작업 상태 저장

주의점:

- Uvicorn worker를 여러 개 실행하면 프로세스마다 별도 queue와 Runner가 생긴다.
- 재시작 시 메모리 queue의 작업은 사라질 수 있다.
- SQLite의 `queued` 또는 `running` 작업을 시작할 때 복구하는 로직이 필요하다.
- 규모가 커지면 FastAPI와 scanner worker를 별도 프로세스로 분리한다.

## 운영 로그와 스캔 결과 구분

운영 로그는 프로세스 시작·종료, 템플릿 실패, queue 상태, 예외, 디스크 부족 등 프로그램 상태를 확인하기 위한 데이터다.

스캔 결과는 대상, template ID, 심각도, 탐지 시각, matcher와 탐지 근거처럼 사용자가 조회해야 하는 업무 데이터다. 스캔 결과를 일반 로그 파일에서 다시 파싱하지 않는다.

## 운영 로그 저장 방식

### 권장: journald만 사용

```text
Python logging
  -> stdout / stderr
      -> systemd-journald
```

systemd를 사용한다면 별도의 `scanner.log`를 동시에 만들지 않는다.

전역 journald 설정 예시:

```ini
[Journal]
SystemMaxUse=256M
SystemKeepFree=5G
MaxRetentionSec=7day
Compress=yes
```

위 설정은 스캐너만이 아니라 시스템 전체 journal에 적용된다. 다른 서비스의 로그도 중요하면 `SystemMaxUse=512M` 정도를 사용한다.

### 파일 로그가 필요한 경우

systemd를 사용하지 않을 때만 Python의 `RotatingFileHandler`를 사용한다.

- 로그 파일당 10MB
- 백업 5개
- 총 약 60MB 이하
- 기본 레벨 INFO
- DEBUG는 임시 활성화

파일 로그와 journald를 동시에 영구 저장하지 않는다.

## 로그 레벨 정책

### INFO

- 스캔 시작과 종료
- scan ID와 대상 수
- 사용한 template 수
- 총 요청 수, match 수, error 수
- 설정 변경

### WARNING

- 개별 host timeout의 반복 집계
- queue 포화
- 응답 크기 초과
- 범위 밖 대상 차단
- 디스크 여유 공간 임계치 접근

### ERROR

- 템플릿 컴파일 실패
- SQLite 쓰기 실패
- worker 비정상 종료
- 스캔을 계속할 수 없는 예외

### DEBUG

- 개별 요청 URL
- header 요약
- matcher 평가 과정
- redirect 과정

DEBUG에서도 Authorization, Cookie, API key, password 등은 마스킹한다. 정상적으로 실패한 모든 포트 연결이나 timeout을 한 줄씩 INFO로 남기지 않고, 스캔 종료 시 종류별 개수로 집계한다.

## SQLite 저장 구조

### scan 테이블

```text
scan_id
target
status
created_at
started_at
finished_at
template_count
request_count
matched_count
error_count
cancel_requested
```

### finding 테이블

```text
finding_id
scan_id
template_id
severity
protocol
matched_at
matcher_name
extracted_values
evidence_summary
created_at
```

### 오류 집계 테이블

모든 오류 원문을 저장하기보다 다음처럼 집계한다.

```text
scan_id
error_type
host
count
last_message
last_seen_at
```

## 저장하지 않을 데이터

- 성공한 모든 HTTP 요청
- 모든 응답의 전체 body와 header
- payload의 모든 조합
- 같은 timeout의 반복 로그
- 정상적인 비탐지 결과 전체
- 다운로드한 대용량 파일

## 선택적으로 저장할 데이터

취약점이 탐지된 경우에만 요청 method와 URL, 민감정보를 제거한 일부 header, HTTP status, matcher 이름, 일치한 짧은 snippet과 재현에 필요한 최소 정보를 저장한다.

### 증거 저장 모드

| 모드 | 동작 |
|---|---|
| `none` | 요청·응답 원문을 저장하지 않음 |
| `findings_only` | 탐지된 결과의 제한된 증거만 저장. 기본값 |
| `debug` | 전체 요청·응답을 임시 저장 |

`debug` 모드는 자동 만료 시간을 두고 수동으로 다시 켜야 하도록 설계한다.

## 응답과 증거 크기 제한

- 네트워크에서 읽을 response body: 기본 최대 512KB
- 탐지 결과에 저장할 response snippet: 64KB 이하
- 저장할 raw evidence: 건당 최대 256KB
- 초과 데이터에는 `truncated=true` 표시
- 압축하더라도 압축 해제 후 크기 제한 검사

`Content-Length`만 믿지 않고 실제로 읽은 byte 수를 제한한다.

## 50GB 저장공간 예산

| 구분 | 권장 한도 |
|---|---:|
| systemd journal | 256~512MB |
| SQLite 결과 | 1~2GB |
| raw evidence | 2GB |
| templates | 1GB 이하 |
| 임시 파일 | 1GB 이하 |
| 반드시 남길 여유 공간 | 최소 5GB, 권장 10GB |

스캐너 관련 데이터 전체에는 우선 5GB 정도의 상한을 둔다.

## 디스크 보호 규칙

다음 조건 중 하나가 충족되면 새 스캔을 거부한다.

- 남은 공간이 5GB 미만
- 전체 공간의 15% 미만
- 스캐너 데이터 사용량이 설정한 상한 초과

스캔 중 임계치에 도달하면 DEBUG/raw evidence 저장 중단, 신규 작업 접수 중단, storage warning 기록, DB flush와 안전한 종료 순서로 대응한다.

## 보존 정책

| 데이터 | 보존 기간 |
|---|---:|
| 운영 로그 | 7일 |
| 심각한 오류 | 최대 30일 |
| 완료한 일반 scan 요약 | 30일 |
| findings | 90일 또는 명시적 삭제까지 |
| raw evidence | 7~30일 |
| 실패한 작업 상세 | 14일 |
| 임시 파일 | 작업 종료 즉시 삭제 |

크기 제한과 기간 제한을 함께 적용하며, 둘 중 먼저 도달한 기준으로 오래된 데이터를 삭제한다.

## SQLite WAL 주의점

SQLite를 WAL 모드로 사용할 경우 database 파일 외에 `-wal`, `-shm` 파일이 생길 수 있다.

- WAL 파일도 디스크 사용량 계산에 포함한다.
- 정기적으로 checkpoint한다.
- 종료 시 DB 연결을 정상적으로 닫는다.
- DB 백업 시 database와 WAL 상태를 함께 고려한다.
- 무제한 WAL 증가를 방지한다.

## 권장 운영 구성

```text
Nginx
  -> Uvicorn worker 1개
      -> FastAPI
          -> bounded job queue
              -> ScanRunner 1개
                  -> protocol workers 20개
                      -> result writer queue 1개
                          -> SQLite

stdout/stderr
  -> systemd-journald, 최대 256~512MB
```
