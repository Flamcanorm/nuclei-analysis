# 외부 설계 평가 검토와 적용 우선순위

## 결론

Claude의 평가는 전반적으로 타당하고 실제 구현에서 발생할 수 있는 문제를 잘 짚었다. 특히 **요청 총량 제한, 대상별 속도 제한, 인증·인가, IP 정규화**는 초기 설계에 바로 반영할 가치가 크다.

다만 평가의 일부는 프로그램이 처음부터 Nuclei와 비슷한 DSL, payload, YAML 템플릿 엔진을 구현한다는 가정을 두고 있다. 현재 방향은 Nuclei와 연동하지 않는 독립 Python 스캐너이며, 첫 버전은 Python 함수로 검사 규칙을 작성한다. 따라서 DSL·payload·템플릿 캐시 문제는 중요한 지적이지만 **현재 MVP의 즉시 차단 요소는 아니고 향후 템플릿 기능을 만들 때의 필수 조건**이다.

## 항목별 판단

| 번호 | 평가 항목 | 판단 | 적용 시점 |
|---|---|---|---|
| 1 | DSL evaluator와 ReDoS | 타당함. 문자열 DSL을 성급히 만들지 않는 것이 더 안전함 | 자체 YAML/DSL을 도입할 때 |
| 2 | Payload 조합 폭발 | 매우 타당함. rate limit과 총 작업량 제한은 서로 다른 문제임 | payload 기능을 만들기 전 |
| 3 | 템플릿 무결성·출처 | 타당함. Git만으로 런타임 신뢰가 보장되지는 않음 | 템플릿 등록 기능을 만들기 전 |
| 4 | 컴파일 캐시 제한 | 타당하지만 현재는 이른 최적화임 | 템플릿 수와 메모리 사용량이 늘 때 |
| 5 | 대상별 rate limit | 매우 타당하며 초기 HTTP/TCP 검사부터 필요함 | MVP 초기 |
| 6 | 결과 중복 제거 키 | 타당함. 저장 구조를 만들 때 정의해야 함 | SQLite 결과 저장 단계 |
| 7 | 인증·인가 | 매우 중요함. LAN의 다른 장비에서 접근하기 전에 필요함 | 외부 접근 전 |
| 8 | IPv4-mapped IPv6 | 타당함. scope 우회 방지에 포함해야 함 | 첫 범위 검증 구현 시 |
| 9 | 실시간 관측 지표 | 방향은 타당함. 처음부터 완전한 Prometheus 운영 환경은 필수 아님 | 작업 큐가 동작하기 시작할 때 |

## 1. DSL evaluator

지적은 맞다. 그러나 가장 안전한 해결책은 복잡한 자체 AST evaluator를 곧바로 만드는 것이 아니라 **첫 버전에서 문자열 DSL 자체를 만들지 않는 것**이다.

초기에는 검사 규칙을 Python 함수로 작성한다.

```python
def status_is_success(status_code: int) -> bool:
    return 200 <= status_code < 300
```

나중에 규칙을 파일로 분리해야 한다면 자유로운 표현식보다 구조화된 연산을 사용한다.

```yaml
checks:
  - field: response.status
    operator: equals
    value: 200
```

허용할 `field`와 `operator`를 고정 목록으로 검증하면 Python AST를 실행할 이유가 줄어든다.

정규식이 필요해질 경우 최소한 다음 제한이 필요하다.

- 정규식 패턴 길이 상한
- 검사할 응답 문자열 길이 상한
- 규칙당 정규식 개수 상한
- 실행 시간 또는 격리된 worker 제한
- backreference나 lookaround가 필요 없다면 선형 시간 계열 정규식 엔진 검토

정규식 타임아웃 하나만으로 안전하다고 보지 않고 입력 크기와 총 작업량도 함께 제한해야 한다.

## 2. Payload 조합 폭발

이 지적은 정확하다. 초당 요청 수 제한은 요청을 천천히 보내게 할 뿐, 작업이 언젠가 끝난다는 것을 보장하지 않는다.

예를 들어 payload가 각각 100개인 목록 세 개라면 곱집합은 다음과 같다.

```text
100 × 100 × 100 = 1,000,000 요청
```

필요한 제한:

- 규칙 하나의 예상 요청 수
- 스캔 작업 전체의 최대 요청 수
- 대상 하나의 최대 요청 수
- 스캔 전체 실행 시간
- redirect와 retry를 포함한 실제 요청 수
- 취소 확인 간격

곱셈 계산도 상한을 넘는 순간 계산을 중단하는 방식으로 구현한다. 모든 조합을 메모리의 list로 생성하지 말고 generator로 하나씩 생성한다.

첫 버전에는 payload 조합 기능을 넣지 않으므로 현재는 `max_requests_per_job` 같은 전체 예산만 먼저 둔다.

## 3. 템플릿 무결성과 출처

Git 변경 이력과 리뷰는 좋은 운영 절차지만 그것만으로 실행 시점의 파일 변조까지 막지는 못한다.

템플릿 기능을 도입한다면 다음 정책이 필요하다.

- 일반 사용자의 API 업로드는 기본 비활성화
- 관리자만 별도 검토 절차를 거쳐 등록
- 템플릿 디렉터리를 실행 프로세스에서 읽기 전용으로 사용
- 파일 내용 해시와 버전 기록
- 등록자, 검토자, 변경 시간 감사 기록
- Pydantic의 엄격한 스키마와 알 수 없는 필드 거부
- 최대 요청 수, 정규식, payload 크기 등의 정적 검사
- shell, Python 코드, 임의 파일 경로, 외부 모듈 호출 금지

현재 MVP는 Python 코드에 고정된 소수의 규칙만 사용하므로 템플릿 업로드 위협 면적이 없다.

## 4. 컴파일 캐시

캐시는 템플릿 엔진이 생긴 이후의 문제다. 현재 단계에서 먼저 만들 필요는 없다.

필요해질 때는 항목 개수만 제한하기보다 메모리 사용량을 함께 고려한다.

- 최대 캐시 항목 수
- 예상 최대 바이트 수
- LRU 제거
- 내용 해시 + 스키마 버전 + compiler 버전을 캐시 키에 포함
- 템플릿 변경 시 이전 항목 제거
- payload 전체 조합 결과는 캐시하지 않음
- 실제 RSS 메모리 측정 후 상한 조정

내용 해시를 사용하면 변경된 템플릿은 자연스럽게 다른 키가 되지만, 이전 캐시 항목을 언제 제거할지는 별도 정책이 필요하다.

## 5. 전역 제한과 대상별 제한

이 지적은 초기 설계에 바로 반영해야 한다.

```text
전체 장비 보호
  -> global concurrency limit
  -> global requests-per-second

대상 장비 보호
  -> target concurrency limit
  -> target requests-per-second

작업 종료 보장
  -> max requests per job
  -> max scan duration
```

대상별 limiter의 키는 사용자가 입력한 hostname 문자열만 사용하면 안 된다. 여러 hostname이 같은 장비를 가리킬 수 있으므로 검증 후의 **정규화된 IP + 포트**를 기준으로 잡는 편이 낫다.

host limiter 딕셔너리 자체도 무한히 커질 수 있으므로 최근 사용 시간이 오래된 항목을 제거하거나 최대 개수를 제한한다.

라즈베리파이의 초기 예시값은 실제 성능 측정 전의 보수적 출발점일 뿐이다.

```text
scan worker: 1
global concurrency: 5
target concurrency: 2
global RPS: 5
target RPS: 2
작업당 요청 수: 100
작업 최대 시간: 5분
```

검사 목적과 라즈베리파이 모델을 측정한 후 조정한다.

## 6. 결과 중복 제거

중복 제거 범위를 구분해야 한다.

- **같은 스캔 내부 중복**: 한 번만 저장
- **서로 다른 스캔의 동일 취약점**: 삭제하지 않고 재발견 이력으로 남김

같은 스캔 내부의 예시 키:

```text
scan_id
+ canonical_target
+ rule_id
+ location
+ normalized_evidence_hash
```

응답 시간, Date 헤더, 동적 토큰처럼 매번 달라지는 값은 evidence hash를 만들기 전에 제거한다. 그렇지 않으면 같은 문제도 매번 다른 결과로 판단된다.

장기적으로는 취약점의 정체성을 나타내는 `finding_fingerprint`와 각 스캔에서 발견된 `occurrence`를 분리하는 구조가 적합하다.

## 7. 인증과 인가

다른 컴퓨터가 라즈베리파이 API에 접속하기 전에는 반드시 필요하다.

MVP:

- 하나의 관리자 API 키
- 키는 코드나 Git이 아니라 환경변수 또는 권한 제한 파일에 저장
- 모든 `/scans` 계열 API에 인증 적용
- API 키가 사용할 수 있는 CIDR allowlist 연결
- 실패한 인증과 작업 생성은 민감정보 없이 감사 로그 기록
- 키 비교는 timing 차이가 적은 안전한 비교 사용

사용자가 여러 명이 되면 다음 단계에서 권한을 분리한다.

```text
viewer: 상태와 결과 조회
operator: 허용 범위 안에서 스캔 실행
admin: 사용자, 허용 범위, 규칙 관리
```

Nginx를 설치했다는 사실만으로 API 인증이 생기는 것은 아니다.

## 8. IP 주소 정규화와 scope 검증

IPv4-mapped IPv6는 실제로 고려해야 한다.

```python
import ipaddress


def normalize_ip(value: str):
    address = ipaddress.ip_address(value)
    if isinstance(address, ipaddress.IPv6Address) and address.ipv4_mapped:
        return address.ipv4_mapped
    return address
```

예를 들어 `::ffff:192.168.1.10`은 정규화 후 `192.168.1.10`으로 CIDR 정책을 확인한다.

추가로 확인할 항목:

- loopback
- link-local
- unspecified와 multicast
- IPv6 zone identifier 입력 정책
- DNS가 반환한 모든 A/AAAA 주소
- redirect 목적지
- DNS 확인 시점과 실제 연결 시점 사이의 주소 변경
- 같은 IP를 다른 표기로 표현하는 입력

URL 문자열만 검사하지 말고 실제 연결에 사용될 정규화된 IP를 기준으로 허용 범위를 판단해야 한다.

## 9. 관측 가능성

평가의 방향은 맞지만 처음부터 별도의 Prometheus 서버까지 설치할 필요는 없다. 애플리케이션이 `/metrics`를 제공하고 필요할 때 수집기를 붙이는 단계적 접근이 가능하다.

초기 핵심 지표:

- 현재 queue 깊이와 최대 크기
- 실행 중인 worker 수
- queued, completed, failed, cancelled 누적 수
- 스캔 실행 시간
- 네트워크 timeout 수
- 전역·대상별 rate limit 대기 횟수
- SQLite 파일 크기
- 디스크 남은 용량
- 프로세스 RSS 메모리

target URL이나 IP를 metric label로 넣으면 민감정보 노출과 높은 cardinality 문제가 생길 수 있으므로 넣지 않는다. `/health`는 프로세스 생존 확인, `/ready`는 DB와 worker가 실제 작업을 받을 수 있는지 확인하는 용도로 구분할 수 있다.

## 이 평가에 추가할 보완점

외부 평가에 더해 다음 항목도 초기 설계에서 중요하다.

### 요청 예산은 재시도까지 포함

timeout 재시도와 redirect도 총 요청 수에 포함하지 않으면 제한을 우회하게 된다.

### 응답 크기는 스트리밍으로 제한

응답 전체를 메모리에 받은 후 길이를 검사하면 이미 메모리를 사용한 뒤다. 읽는 과정에서 최대 바이트를 넘으면 중단해야 한다.

### SQLite 쓰기 병목

여러 검사기가 동시에 직접 쓰기보다 저장 작업을 짧게 유지하고 한정된 writer 경로를 사용하는 편이 안정적이다.

### 정상 종료와 전원 차단

라즈베리파이는 갑작스럽게 전원이 꺼질 수 있다. WAL 모드, 짧은 transaction, 시작 시 `running` 작업 복구 정책이 필요하다.

### 민감정보

로그뿐 아니라 `evidence`, 오류 메시지, metric label에도 Cookie, Authorization, 토큰, 비밀번호가 들어가지 않게 해야 한다.

## 실제 적용 우선순위

### P0: 첫 실제 네트워크 요청 전에 필수

1. 단일 API 키 인증
2. 정규화된 IP 기반 CIDR allowlist
3. 전역 및 대상별 동시성·RPS 제한
4. 작업당 최대 요청 수와 최대 실행 시간
5. 응답 크기와 redirect 제한
6. 취소와 정상 종료

### P1: SQLite와 운영 단계

1. 중복 키와 재발견 이력 설계
2. queue, worker, 실패, 시간, 메모리, 디스크 지표
3. 로그와 evidence의 민감정보 제거
4. 재부팅 후 상태 복구

### P2: 자체 YAML·DSL을 실제로 도입할 때

1. 자유로운 문자열 DSL 대신 구조화된 연산 우선
2. 정규식 패턴·입력·실행 제한
3. payload 예상 요청 수 정적 계산
4. 템플릿 출처, 승인, 해시, 읽기 전용 배포
5. 크기가 제한된 LRU 컴파일 캐시

## 최종 판단

Claude의 9개 지적을 버릴 것은 없다. 다만 현재 개발을 시작하기도 전에 DSL evaluator, payload generator, 템플릿 캐시를 모두 설계하면 오히려 범위가 커진다.

현재 프로그램에 가장 맞는 판단은 다음과 같다.

> 첫 버전에서는 YAML, DSL, payload 조합을 만들지 않고 Python 함수로 소수의 안전한 검사만 구현한다. 대신 인증, IP 범위 검증, 전역·대상별 요청 제한, 총 요청 예산, timeout과 관측 지표는 처음부터 넣는다. 규칙이 늘어 템플릿이 정말 필요해진 시점에 Claude가 지적한 DSL·정규식·무결성·캐시 통제를 설계 조건으로 적용한다.
