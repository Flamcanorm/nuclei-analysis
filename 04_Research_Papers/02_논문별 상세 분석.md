## 1. Bitscanner

### 연구 목적

웹 애플리케이션을 크롤링하고, 미리 정의한 30가지 공격 패턴으로 취약점을 빠르게 검사하는 자동 스캐너를 제안한다.

### 처리 흐름

```text
웹사이트 입력
    ↓
전체 깊이 크롤링
    ↓
페이지·Form·JSON·XML·AJAX 분석
    ↓
GET·POST 매개변수 추출
    ↓
공격 패턴을 매개변수에 삽입
    ↓
조작된 HTTP 요청 전송
    ↓
응답을 오류 패턴 DB와 비교
    ↓
취약점 보고서 생성
```

`매개변수`는 사용자가 서버에 전달하는 값이다.

```text
/user?id=10
       │  └─ 값
       └─ 매개변수 이름
```

Bitscanner는 이러한 값에 SQL Injection, XSS 등의 공격 문자열을 삽입하여 서버 반응을 확인한다.

### Nuclei와 공통점

```text
Bitscanner 공격 패턴 DB
≈ Nuclei Template

Bitscanner 응답 패턴 비교
≈ Nuclei Matcher

Bitscanner 보고서 생성
≈ Nuclei Output Writer
```

두 프로그램 모두 외부에서 요청을 보내고 응답이 미리 정의한 조건과 일치하는지 검사한다.

### 차이점

- Bitscanner는 웹사이트를 직접 크롤링하고 입력 매개변수를 자동 탐색한다.
- Nuclei는 Template에 정의된 경로와 요청을 실행하는 방식이 중심이다.
- Nuclei는 HTTP뿐 아니라 DNS, SSL, TCP, Headless, Cloud 등도 지원한다.
- Bitscanner는 논문 기준 30개 취약점 유형에 집중한다.

### 실험 결과

- 87개의 웹 애플리케이션을 검사했다.
- 3개의 웹 애플리케이션에서 Acunetix·Arachni와 속도를 비교했다.
- 논문은 오탐률 0%라고 주장한다.
- PDF, XML, HTML, CSV 및 대시보드 보고서를 제공한다.

### 한계

오탐률 0%라는 수치는 다음 사항을 확인한 후 받아들여야 한다.

- 실제 취약점의 정답을 누가 결정했는가?
- 전문가가 모든 결과를 수동으로 검증했는가?
- 실험 대상이 공개되지 않아 재현이 어렵다.
- 속도 비교 대상이 3개로 적다.
- 결과가 30개 취약점 유형에 한정된다.

## 2. 홈페이지의 웹취약점분석모델에 관한 실증적 연구

### 연구 목적

단순히 발견된 취약점 개수만 세는 방식에서 벗어나, 홈페이지 제작 형태와 정보보안 요소의 관계를 함께 분석하는 모델을 제안한다.

### 처리 흐름

```text
홈페이지 운영환경 확인
    ↓
자체 제작 또는 CMS 종류를 7가지로 분류
    ↓
점검 대상 기능과 경로 결정
    ↓
취약점을 3가지 기준으로 분류
├─ 기술 기준
├─ 관리 기준
└─ 인증 기준
    ↓
자동 점검
    ↓
수동 점검으로 오탐 제거
    ↓
PoC로 실제 취약점 확인
    ↓
기밀성·무결성·인증성과의 관계 분석
```

### 주요 결과

자동 점검 결과를 수동으로 다시 검증했을 때 다음 비율로 취약점이 확인되었다.

- SQL Injection: 약 50%
- XSS: 약 90%

자동 도구가 출력한 결과가 모두 실제 취약점은 아니라는 사실을 보여준다.

### Nuclei 관련성

```text
Nuclei 탐지 결과
    ↓
AI 또는 사람의 추가 검증
    ↓
실제 취약 가능성 분석
    ↓
사람이 최종 판단
```

Nuclei 결과에 AI 분석을 추가해야 하는 연구 배경으로 활용할 수 있다.

### 한계

- 중소기업 홈페이지 중심이다.
- 홈페이지 제작 형태와 CMS 분석이 중심이다.
- 새로운 취약점 탐지 알고리즘은 제안하지 않는다.
- 복잡한 취약점은 여전히 컨설턴트의 경험에 영향을 받는다.

## 3. AI 기반 보안 취약점 탐지 시스템

### 연구 목적

고정 규칙을 사용하는 OWASP ZAP의 한계를 머신러닝으로 보완하려는 연구다.

### 처리 흐름

```text
데이터 수집
├─ CWE 데이터
├─ OWASP ZAP 로그
├─ GitHub 저장소
└─ 실시간 보안 이벤트 로그
    ↓
전처리
├─ 노이즈 제거
├─ 정상·공격 레이블 부착
└─ SMOTE로 데이터 불균형 보완
    ↓
학습 데이터 80%
테스트 데이터 20%
    ↓
Random Forest 학습
    ↓
Kafka를 통한 실시간 처리
    ↓
정상 또는 취약 요청 예측
```

### SMOTE

정상 데이터보다 공격 데이터가 지나치게 적으면 AI가 대부분의 입력을 정상으로 판단할 수 있다.

SMOTE는 적은 쪽의 데이터를 참고하여 인공 학습 데이터를 추가하는 기법이다.

### 결과

- AI 평균 정확도: 91%
- OWASP ZAP 대비 정확도: 약 6% 향상
- AI 오탐률: 10%
- OWASP ZAP 오탐률: 12%
- AI 미탐률: 12.5%
- OWASP ZAP 미탐률: 14%
- AI 평균 탐지 시간: 9초
- OWASP ZAP 평균 탐지 시간: 10초
- AI F1-score: 0.91
- OWASP ZAP F1-score: 0.87

### 중요한 한계

AI와 OWASP ZAP을 동일한 시험 환경에서 비교하지 않았다.

```text
OWASP ZAP
└─ OWASP Benchmark의 기존 결과 사용

AI 시스템
└─ 별도로 전처리한 데이터셋 사용
```

서로 다른 시험지의 점수를 비교한 것과 비슷하므로, AI가 반드시 6% 우수하다고 확정하기 어렵다.

그 밖의 한계는 다음과 같다.

- SQL Injection, XSS, CSRF 중심이다.
- RCE, 경로 조작, 역직렬화 등은 충분히 다루지 못했다.
- 새로운 환경에서의 일반화 성능을 검증하지 못했다.
- 모델 업데이트가 수동이다.
- 실제 대규모 네트워크의 실시간 성능을 충분히 검증하지 못했다.

## 4. 정적·동적 분석 크로스 체크

### 연구 목적

정적 분석과 동적 분석 결과를 교차 검증하여 오탐·미탐·과탐을 줄이고, 탐지 정확도를 포함한 애플리케이션 위험도를 계산한다.

### 처리 흐름

```text
소스코드 정적 분석
    ↓
의심되는 취약점 발견
    ↓
맞춤형 정적 분석 규칙 생성
    ↓
Exploit 코드 생성
    ↓
실행 중인 애플리케이션에 동적 검증
    ↓
두 분석 결과 크로스 체크
    ↓
취약점 정확도와 위험도 계산
```

### Nuclei 관련성

```text
SAST가 소스코드에서 의심 지점 발견
    ↓
해당 지점을 검사하는 Nuclei Template 실행
    ↓
실제 응답에서 취약점 재검증
```

### 결과와 한계

- CWE/SANS Top 25 중 상위 10개 항목을 기준으로 비교했다.
- 정적·동적 분석을 결합한 프로토타입을 구현했다.
- 기존 도구보다 전반적으로 많은 정탐을 보였다.
- CWSS 위험도와 탐지 정확도를 결합했다.
- 일부 항목에서는 탐지 수 증가와 함께 오탐 수도 증가했다.

더 많이 탐지했다는 사실만으로 모든 결과가 정확하다는 뜻은 아니다.

## 5. LSTM 기반 HAST 아키텍처

### 연구 목적

```text
SAST
소스코드 검사
     ↘
      HAST
     ↗
DAST
실행 중인 애플리케이션 검사
     +
LSTM
HTTP 요청 시퀀스 분석
```

[[05_논문 전용 용어 사전#^term-sast|SAST]], [[05_논문 전용 용어 사전#^term-dast|DAST]]와 [[05_논문 전용 용어 사전#^term-lstm|LSTM]]을 하나의 보안 [[05_논문 전용 용어 사전#^term-architecture|아키텍처]]로 결합한다.

```text
개발자가 작성한 소스코드
        ↓
SAST로 코드 내부 검사
        ↓
테스트용 웹 애플리케이션 실행
        ↓
DAST로 외부 공격 요청 전송
        ↓
LSTM으로 요청의 순서와 패턴 분석
        ↓
각 분석 결과 통합
        ↓
최종 취약점 보고서 생성
```

### LSTM을 사용하는 이유

LSTM은 데이터가 나타나는 [[05_논문 전용 용어 사전#^term-sequence|순서]]와 앞뒤 관계를 학습하는 AI 모델이다.

```text
단순 문자열 검사
└─ 요청에 'select'라는 단어가 있는가?

LSTM 분석
└─ 단어·기호·값이 어떤 순서와 관계로 나타나는가?
```

긴 [[05_논문 전용 용어 사전#^term-payload|Payload]]나 여러 요청의 연속적인 특징을 분석하는 데 활용할 수 있다.

LSTM의 `Memory`는 파일을 저장한다는 뜻이 아니다. 앞에서 확인한 특징 중 필요한 정보를 뒤의 판단에 활용한다는 의미다.

### 제안 내용

- HTTP 요청과 Payload를 LSTM으로 분석한다.
- SAST와 DAST 결과를 통합한다.
- 새로운 데이터로 재학습할 수 있다.
- [[05_논문 전용 용어 사전#^term-ci-cd|CI/CD]] 파이프라인과 연결한다.
- 개발부터 운영까지 전 주기 검사를 목표로 한다.

### 가장 중요한 한계

실제 구현과 [[05_논문 전용 용어 사전#^term-quantitative-experiment|정량적인 성능 실험]]을 수행하지 않은 설계 제안 연구다.

- [[05_논문 전용 용어 사전#^term-accuracy|정확도]]와 [[05_논문 전용 용어 사전#^term-false-positive-rate|오탐률]] 측정이 없다.
- LSTM과 다중 분석으로 [[05_논문 전용 용어 사전#^term-computational-cost|연산 비용]]이 커질 수 있다.
- 실제 [[05_논문 전용 용어 사전#^term-latency|지연 시간]]과 [[05_논문 전용 용어 사전#^term-throughput|처리량]] 검증이 필요하다.

이 논문은 성능 증거보다 시스템 구조 참고자료로 사용하는 것이 적절하다.

## 6. 웹사이트 구조화 및 페이지별 동작크기

### 연구 목적

- 검사하지 않은 페이지 발생
- 점검자가 기능을 빠뜨리는 문제
- 점검자마다 검사 범위가 달라지는 문제
- 검사 기간을 객관적으로 계산하기 어려운 문제

이러한 수동 동적 점검의 문제를 줄이는 것이 목적이다.

### 제안 방법

```text
웹사이트의 정보구조 IA 작성
    ↓
세부 페이지 식별
    ↓
페이지를 7가지 동작 기능으로 분류
    ↓
페이지의 매개변수 수 확인
    ↓
페이지별 동작크기 SoA 계산
    ↓
전체 웹사이트 점검 규모 계산
    ↓
하루 점검 가능량과 전체 기간 산정
```

SoA는 페이지를 검사하는 데 필요한 작업량을 나타내는 값이다. 이 논문에서는 주로 매개변수 개수를 사용한다.

### Nuclei 관련성

Nuclei에 다음과 같은 검사 범위 보고 기능을 추가할 때 활용할 수 있다.

```text
전체 발견 엔드포인트
실제로 검사한 엔드포인트
검사하지 못한 엔드포인트
각 엔드포인트에 적용한 템플릿
```

### 한계

- 수동 점검 중심이다.
- 매개변수 개수만으로 작업량을 계산한다.
- 매개변수별 중요도를 반영하지 않는다.
- 취약점 판정 알고리즘을 개선하는 연구는 아니다.

### 연구 목적

기존 실무에서는 Proxy Tool을 이용한 동적 진단과 자동 정적 진단 도구를 함께 사용한다. 그러나 다음 문제가 남는다.

```text
자동 정적 진단
├─ 주석 처리되어 실행되지 않는 코드도 탐지
├─ 문자열 Pattern만 같아도 취약하다고 판단
└─ 실제 처리 Logic과 호출 관계를 놓칠 수 있음

동적 진단
├─ 화면에서 발견한 입력점에 의존
├─ 모든 기능과 Parameter를 찾기 어려움
└─ Dropdown·Hidden Field·내부 처리 Logic을 놓칠 수 있음
```

논문은 소스코드를 먼저 수동 정적 분석하고, 실제 발생 가능성이 있다고 판단한 항목만 동적으로 검증하여 오탐과 미탐을 줄이는 방법을 제안한다.

### 제안 흐름

```text
소스코드와 사용 언어·Framework 확인
    ↓
취약 Pattern과 관련 파일 검색
    ↓
검색 결과를 목록으로 정리
    ↓
주석·미사용 Page·관련 없는 Pattern 제거
    ↓
함수 호출과 검증 Logic을 사람이 추적
    ↓
발생 가능성이 있으면 O, 아니면 X로 분류
    ↓
O로 분류된 위치만 동적으로 검증
    ↓
실제로 재현된 항목만 최종 취약점으로 보고
```

기존 방법은 자동 정적 진단 결과와 동적 진단 결과를 각각 확인한 뒤 중복을 정리한다. 제안 방법은 수동 정적 분석에서 후보를 먼저 좁히고, 가능성이 있는 후보에만 동적 검증을 수행한다.

### 실험 조건

논문은 연구자가 준비한 Sample 사이트 2개를 사용했다.

| 구분 | 사이트 1 | 사이트 2 |
|---|---|---|
| 주요 환경 | ASP 기반 | JSP·Spring Framework 기반 |
| 구현 기능 | 쇼핑몰 기능 | 파일 업로드가 포함된 단일 게시판 |
| 데이터 크기 | 105MB | 5MB |
| 기존 방법 소요 기간 | 5일 | 2일 |
| 제안 방법 소요 기간 | 8일 | 3일 |

논문은 하루 진단 시간을 4시간으로 계산했다. 따라서 사이트 1의 기존 방법은 약 20시간, 제안 방법은 약 32시간이며, 사이트 2는 각각 약 8시간과 12시간에 해당한다.

검사 항목은 다음 4개로 제한했다.

- SQL Injection
- XSS
- 위험한 파일 업로드
- 주요 파일 다운로드

자동 정적 진단 도구는 이름을 공개하지 않고 `진단도구 A`, `진단도구 B`로 표시했다. 두 도구는 각 사이트의 언어를 지원하는 제품으로 선정되었다.

### 사이트 1의 자동 정적 진단 결과

아래 수치는 동적 검증 전, 자동 정적 진단 도구가 출력한 탐지 건수다. 따라서 오탐이 포함되어 있다.

| 검사 항목 | 진단도구 A | 진단도구 B |
|---|---:|---:|
| SQL Injection | 487 | 610 |
| XSS | 911 | 1,010 |
| 위험한 파일 업로드 | 15 | 15 |
| 주요 파일 다운로드 | 10 | 30 |

자동 도구만 사용했을 때 SQL Injection과 XSS 후보가 매우 많이 출력되었다. 논문은 주석 처리된 코드, 실행되지 않는 코드와 실제로 취약하지 않은 Pattern이 포함되어 건수가 커졌다고 설명한다.

### 사이트 1의 방법별 최종 비교

| 검사 항목 | 진단도구 A+동적 진단 | 진단도구 B+동적 진단 | 제안 방법 |
|---|---:|---:|---:|
| SQL Injection | 115 | 115 | 115 |
| XSS | 321 | 487 | 522 |
| 위험한 파일 업로드 | 15 | 15 | 152 |
| 주요 파일 다운로드 | 10 | 10 | 20 |

논문이 설명하는 차이의 원인은 다음과 같다.

- SQL Injection은 세 방법 모두 같은 건수를 확인했다.
- 자동 도구는 사용자가 값을 직접 입력하는 위치를 주로 탐지했다.
- 제안 방법은 입력 위치뿐 아니라 파일을 실제로 등록하는 처리 Logic과 확장자·경로 검증 여부까지 소스에서 확인했다.
- XSS에서는 자동 도구가 Hidden Field 일부를 확인했지만 다른 Parameter를 놓쳤다고 설명한다.
- 파일 업로드와 다운로드에서는 입력 화면뿐 아니라 실제 저장·다운로드 처리 경로를 확인하여 제안 방법의 건수가 증가했다.

### 사이트 2의 자동 정적 진단 결과

| 검사 항목 | 진단도구 A | 진단도구 B |
|---|---:|---:|
| SQL Injection | 1 | 1 |
| XSS | 5 | 5 |
| 위험한 파일 업로드 | 2 | 2 |
| 주요 파일 다운로드 | 2 | 2 |

사이트 2는 규모가 작고 취약 Pattern이 비교적 명확하여 자동 정적 진단 결과가 모두 실제 취약한 것으로 확인되었다고 논문은 설명한다.

### 사이트 2의 방법별 최종 비교

| 검사 항목 | 진단도구 A+동적 진단 | 진단도구 B+동적 진단 | 제안 방법 |
|---|---:|---:|---:|
| SQL Injection | 1 | 1 | 2 |
| XSS | 5 | 5 | 11 |
| 위험한 파일 업로드 | 2 | 2 | 2 |
| 주요 파일 다운로드 | 2 | 2 | 2 |

제안 방법이 추가로 발견한 내용은 다음과 같다.

- SQL Injection: 사용자가 직접 문자열을 입력하는 칸뿐 아니라 Dropdown에서 선택하는 값도 취약할 수 있음을 확인했다.
- XSS: Stored XSS 외에도 DB에 저장되지 않는 Reflected XSS와 다른 사이트로 이동할 때 Script를 삽입할 수 있는 위치 등을 추가로 확인했다.
- 파일 업로드·다운로드: 자동 도구도 입력과 처리 Logic을 탐지하여 세 방법의 결과가 같았다.

### 수치 해석 시 주의할 점

표의 숫자를 그대로 “서로 독립적인 실제 취약점 개수”라고 단정하면 안 된다.

- 논문은 진단 도구 A와 B의 제품명을 공개하지 않았다.
- 두 개의 Sample 사이트와 네 가지 취약점 유형만 실험했다.
- 동일한 원인에서 여러 코드 위치가 탐지됐는지 명확하게 분리하지 않는다.
- 표준 Benchmark나 외부 전문가가 만든 정답표를 사용하지 않았다.
- Precision, Recall, F1-score와 오탐률을 계산하지 않았다.
- 제안 방법은 더 많은 결과를 확인했지만 진단 시간도 약 50~60% 증가했다.

따라서 이 연구는 제안 방법이 두 Sample 사이트에서 자동 도구가 놓친 항목을 추가로 발견했다는 근거는 제공하지만, 모든 웹 애플리케이션에서 항상 더 높은 정확도를 보장한다는 증거는 아니다.

### 연구의 핵심 결론

```text
자동 정적 분석
빠르게 많은 후보를 찾음
    ↓
오탐이 많고 처리 문맥을 놓침

수동 정적 분석
호출 관계와 검증 Logic 확인
    ↓
실제 발생 가능성이 있는 후보 선별

동적 검증
선별된 후보를 실행 중인 사이트에서 재현
    ↓
최종 취약점으로 보고
```

제안 방법은 탐지 수와 신뢰성을 높이는 대신 더 많은 분석 시간이 필요하다. 논문도 실무에서 빠른 결과가 요구되므로 이 절차의 자동화가 필요하다고 결론 내린다.

### Nuclei와 차이점

| 논문의 제안 방법 | Nuclei의 일반적 검사 |
|---|---|
| 소스코드 접근 필요 | 실행 중인 Target에 외부 요청 |
| 사람이 함수 호출과 데이터 문맥 추적 | Template에 정의된 요청과 Matcher 실행 |
| 수동 정적 분석 후 동적 재현 | 주로 블랙박스 DAST |
| 두 Sample 사이트를 깊게 분석 | 많은 Target에 같은 Template을 빠르게 실행 |

두 방식을 연결한다면 SAST나 수동 분석에서 찾은 코드 위치를 Nuclei Template로 동적 재검증할 수 있다.

```text
정적 분석 결과
위험한 Parameter·Endpoint·호출 조건
    ↓
Nuclei Template 작성
    ↓
실제 Target에 제한된 검증 요청
    ↓
Matcher로 재현 여부 판정
```

이 경우에도 Nuclei가 소스코드를 직접 분석한 것은 아니다. 앞 단계에서 발견한 후보를 외부 요청으로 재검증하는 역할이다.

### 한계

- 소스코드를 제공받지 못하면 제안 방법을 적용하기 어렵다.
- 진단자의 코드 분석 능력에 따라 결과가 달라질 수 있다.
- 기존 방법보다 시간이 오래 걸렸다.
- 실험 대상이 연구자가 구현한 두 Sample 사이트로 제한된다.
- SQL Injection, XSS, 파일 업로드, 파일 다운로드 네 항목만 평가했다.
- 자동 도구의 이름과 세부 설정이 공개되지 않아 동일 조건의 재현이 어렵다.

### AI 관련성

논문은 다음 방향을 향후 과제로 제시한다.

```text
단순한 코드 패턴
    ↓
데이터 문맥과 상관관계 분석
    ↓
AI형 자동 정적 진단 도구
    ↓
빠른 시간에 오탐·미탐 감소 시도
```

이 논문은 AI 모델, 학습 데이터, 특징, 정확도나 성능 실험을 제시하지 않는다. 따라서 AI 시스템의 효과를 입증한 논문이 아니라 “수동으로 수행한 문맥 분석을 향후 AI로 자동화할 필요가 있다”고 제안한 연구로 인용해야 한다.

## 8. Black Widow: Blackbox Data-driven Web Scanning

### 연구 목적

현대 웹사이트는 주소만 따라가는 단순 Crawler로는 충분히 검사하기 어렵다. JavaScript 버튼, 로그인, 폼 제출과 같이 이전 행동에 따라 다음 화면이 달라지기 때문이다. Black Widow는 웹 애플리케이션의 상태와 상태 사이의 관계를 기록하여 더 깊은 화면과 저장형 XSS 같은 취약점에 도달하려고 한다.

### 처리 흐름

```text
시작 URL
    ↓
링크·폼·프레임·JavaScript 이벤트 발견
    ↓
클릭·입력·제출로 새로운 상태 이동
    ↓
어떤 행동으로 해당 상태에 왔는지 Navigation Model에 기록
    ↓
임의 표시값을 입력하고 이후 상태에서 다시 나타나는지 추적
    ↓
상태 사이 데이터 의존성과 XSS 가능성 확인
```

여기서 `상태`는 단순 URL만 의미하지 않는다. 같은 URL이라도 로그인 여부, 장바구니 내용, JavaScript로 변경된 화면에 따라 다른 상태가 될 수 있다.

### Nuclei 관련성

- Nuclei는 이미 알고 있는 URL과 Template 검사에 강하다.
- Black Widow는 “검사할 URL과 입력 위치를 어떻게 더 많이 발견하는가?”에 집중한다.
- 두 방식을 연결하면 Crawler가 발견한 Endpoint를 Nuclei의 입력으로 공급할 수 있다.
- Nuclei의 Headless 기능과 비교할 수 있지만, Black Widow의 핵심은 전체 상태 전이와 상태 사이 의존성을 모델링하는 데 있다.

### 한계

- 브라우저 상태를 많이 저장하고 재현해야 하므로 비용이 크다.
- 로그인·CAPTCHA·복잡한 폼은 자동 처리하기 어렵다.
- 연구용 시스템의 결과가 모든 실제 웹사이트에 그대로 일반화된다고 볼 수 없다.

## 9. RESTler: Stateful REST API Fuzzing

### 연구 목적

API 하나씩 따로 호출하면 찾기 어려운 상태 기반 오류를 발견한다. REST API에서는 앞 요청이 만든 값을 뒤 요청에서 사용해야 하는 경우가 많다.

### 생산자와 소비자 관계

```text
POST /users
응답: {"id": 17}
        ↓ id를 생산
GET /users/17
        ↓ id를 소비
DELETE /users/17
```

RESTler는 OpenAPI 문서에서 이런 생산자·소비자 관계를 추론하고 실행 가능한 요청 순서를 만든다.

### 처리 흐름

```text
OpenAPI JSON·YAML
    ↓
Endpoint·Method·Parameter 해석
    ↓
요청 사이 의존성 추론
    ↓
실행 가능한 Request Sequence 생성
    ↓
이전 응답값을 다음 요청에 삽입
    ↓
500 오류와 보안 속성 위반 확인
    ↓
재현 가능한 Replay Log 저장
```

### Nuclei Workflow와 차이

| Nuclei Workflow | RESTler |
|---|---|
| 사람이 Template 실행 순서와 조건을 작성 | OpenAPI에서 요청 의존성을 추론 |
| 알려진 취약점 재현에 강함 | 예상하지 못한 요청 순서와 상태 오류 탐색에 강함 |
| 다양한 프로토콜 지원 | REST API에 집중 |
| 빠른 대량 검사 지향 | 상태 공간을 깊게 탐색 |

### 한계

- 정확한 OpenAPI 문서와 유효한 예제값이 필요할 수 있다.
- 공격적인 Fuzzing은 테스트 서버의 상태를 손상시킬 수 있다.
- 요청 조합이 늘어나면 상태 공간이 매우 커진다.

## 10. SoK: State of the Krawlers

### 연구 목적

웹 보안 측정에서 사용하는 Crawler가 실제로 얼마나 많은 상태와 기능을 발견하는지 공정하게 비교한다. 취약점 Scanner의 탐지 성능 이전에 Crawler의 탐색 성능을 따로 평가해야 한다는 관점을 제공한다.

### 핵심 질문

```text
탐지 결과가 0개인 이유
├─ 실제로 취약점이 없음
└─ Crawler가 취약한 페이지에 도달하지 못함
```

두 경우는 결과 화면에서는 같아 보일 수 있지만 의미가 다르다.

### Nuclei 관련성

Nuclei에서 `0 matches`가 나와도 모든 기능이 검사되었다는 뜻은 아니다. 다음 정보가 필요하다.

- 선택된 Template 수
- 실제 실행된 Template 수
- 도달한 URL과 입력점
- 인증·WAF·Timeout 때문에 검사하지 못한 항목
- 조건 불일치로 실행되지 않은 Template

이 논문은 [[04_Nuclei와 AI 기능 연결#검사 범위와 미실행 원인 보고서|검사 범위 보고서]] 아이디어의 직접적인 선행연구다.

## 11. NAVEX

### 연구 목적

동적 웹 애플리케이션에서 Crawler가 더 많은 실행 경로에 도달하도록 입력값을 생성하고, 발견된 취약점에 대해 실제 Exploit 경로를 만든다.

### 처리 흐름

```text
Crawler가 링크·폼·JavaScript 수집
    ↓
실행 경로와 입력 조건 분석
    ↓
제약조건 풀이로 통과 가능한 입력 생성
    ↓
더 깊은 페이지와 코드 경로 도달
    ↓
취약점 후보와 Exploit 경로 생성
```

### Nuclei 관련성

Nuclei Template은 검사할 요청을 사람이 구체적으로 작성한다. NAVEX는 프로그램 분석으로 입력 조건을 풀어 새로운 요청을 생성한다. Nuclei에 그대로 합치기에는 복잡하지만 “고정 Payload가 폼 검증에 막혔을 때 입력 조건을 어떻게 알아낼 것인가?”라는 연구 질문을 제공한다.

## 12. Spider-Scents

### 연구 목적

웹 Scanner가 데이터베이스 값을 변경하다가 애플리케이션을 망가뜨리는 문제를 감지하고, 어느 변경이 원인인지 찾아 복구한다.

### 처리 흐름

```text
웹 요청 전송
    ↓
데이터베이스 변경 관찰
    ↓
웹 페이지가 기준 상태와 달라졌는지 비교
    ↓
문제가 생기면 원인이 된 Cell 확인
    ↓
해당 값 복구
```

### Nuclei 관련성

Nuclei의 Rate Limiter는 요청 속도를 제어하지만 대상의 데이터 상태가 망가졌는지를 직접 판단하는 기능과는 다르다. Spider-Scents는 검사 속도뿐 아니라 검사로 발생한 상태 변화를 안전성 지표로 삼는다는 점에서 참고할 가치가 있다.

## 13. SQIRL

### 연구 목적

고정된 SQL Injection Payload 목록만 반복하지 않고, 검사 결과의 피드백을 이용해 다음 Payload 변형을 학습한다.

### 처리 흐름

```text
입력 위치 발견
    ↓
현재 SQL Injection Payload 전송
    ↓
HTML 응답·SQL Query·Log 피드백 수집
    ↓
강화학습 Agent가 다음 변형 선택
    ↓
성공 가능성이 높은 Payload 탐색
```

### Nuclei 관련성

Nuclei는 Template과 Payload에 정의된 값을 빠르고 재현 가능하게 실행한다. SQIRL은 실행 결과를 이용해 다음 입력을 바꾼다. Nuclei에 적용한다면 AI가 최종 취약 여부를 판정하기보다, 제한된 안전 범위 안에서 다음 시험값의 우선순위를 정하는 방식이 적합하다.

### 한계

- 데이터베이스나 Log처럼 내부 피드백이 필요해 그레이박스 성격이 강하다.
- 학습과 탐색에 시간이 필요하다.
- 학습된 정책이 다른 기술 스택에서도 유효한지 검증해야 한다.

## 14. WHIP

### 연구 목적

정적 분석 도구 하나가 끊어진 데이터 흐름을 다른 정적 분석 도구의 정보로 보완하여 복잡한 취약점을 찾는다.

### 핵심 아이디어

```text
SAST A가 추적을 중단한 위치
        ↓
SAST B의 분석 결과에서 대체 경로 탐색
        ↓
분석용 경로를 보완
        ↓
두 도구가 각자의 약점을 보충
```

### Nuclei 관련성

서로 다른 Scanner 결과를 단순히 한 표에 합치는 것과 다르다. 한 도구의 중간 분석 결과가 다른 도구의 분석을 계속 진행하게 만든다는 점이 핵심이다. Nuclei에서는 Template 결과, 기술 탐지, WAF 탐지, 인증 상태 같은 사실을 다음 검사 계획의 입력으로 사용하는 연구와 연결할 수 있다.

## 15. PentestGPT

### 연구 목적

LLM이 긴 침투 테스트 과정에서 전체 진행 상태를 잃어버리는 문제를 줄이기 위해 작업을 모듈로 분리한다.

### 구조

```text
사용자와 도구 출력
    ↓
Reasoning Module
현재 상황과 다음 목표 판단
    ↓
Generation Module
실행할 명령이나 작업 생성
    ↓
Parsing Module
긴 실행 결과에서 중요한 사실 추출
    ↓
다시 Reasoning Module에 전달
```

### Nuclei 관련성

Nuclei에 AI를 붙일 때도 다음 책임을 분리해야 한다.

- Nuclei Matcher: 확정적인 탐지 조건 판정
- AI: 결과 설명, 다음 수동 확인 단계 제안
- 사람: 최종 취약 여부와 보고 여부 결정

PentestGPT의 성능 수치는 특정 Benchmark와 모델 조건에서 나온 결과다. 일반 인터넷 대상에서 같은 성공률을 보장한다는 뜻은 아니다.

## 16. MLLM-Assisted Web Crawler

### 연구 목적

HTML 구조만 보는 Crawler가 이해하기 어려운 화면 요소를 멀티모달 LLM이 해석하여 다음 상호작용을 선택하도록 돕는다.

### 처리 흐름

```text
현재 웹 화면과 DOM
    ↓
클릭·입력 가능한 요소 수집
    ↓
MLLM이 요소의 의미와 다음 행동 판단
    ↓
브라우저에서 행동 실행
    ↓
새로운 화면과 기능 발견
    ↓
Fuzzing 대상 확대
```

### Nuclei 관련성

AI가 Matcher 대신 취약점을 최종 판정하는 기능보다, Headless 탐색에서 로그인·메뉴·폼의 의미를 이해하도록 보조하는 기능에 가깝다. 다만 화면을 외부 AI에 전송하면 개인정보와 인증정보가 포함될 수 있으므로 Redaction과 로컬 모델 사용을 고려해야 한다.

## 17. 코드 생성 AI를 이용한 웹 취약점 점검 방법

### 논문 정보

- 제목: `코드 생성 AI를 이용한 웹 취약점 점검 방법에 관한 연구`
- 영문 제목: `A Study on Web Vulnerability Assessment Methods Using Code Generation AI`
- 저자: 박영식·윤종필·현선진·임종태
- 학술지: 한국차세대컴퓨팅학회 논문지
- 권·호·쪽: 제21권 제4호, 20~30쪽
- 투고일: 2025년 3월 18일
- 심사일: 2025년 3월 23일
- 게재 확정일: 2025년 8월 18일
- DOI: [10.23019/kingpc.21.4.202508.002](https://doi.org/10.23019/kingpc.21.4.202508.002)

### 연구 목적

웹 Scanner는 빠르지만 Pattern 중심이라 오탐과 미탐이 있고, RPA는 로그인과 업무 흐름을 자세히 자동화할 수 있지만 시나리오 작성에 시간이 많이 든다. 논문은 코드 생성 AI에 자연어로 작업을 설명하여 Selenium 기반 점검 코드를 만들면 두 방식의 장점을 결합할 수 있다고 본다.

```text
웹 Scanner
빠른 자동 탐색
    +
RPA
로그인·입력·클릭 등 사용자 행동 자동화
    +
코드 생성 AI
자연어 설명을 Selenium 코드로 변환
    ↓
반복 가능한 웹 취약점 점검과 증적 생성
```

### 여기서 코드 생성 AI가 하는 일

이 논문에서 AI가 웹사이트를 직접 이해하고 독립적으로 취약 여부를 결정하는 것은 아니다. 점검자가 다음 정보를 Prompt로 제공한다.

- 접속할 URL
- 로그인 ID와 Password를 넣을 Field
- 클릭할 Button
- 이동할 Page
- 검사할 Parameter
- 검사할 취약점 유형
- 사용할 Payload 또는 Payload 생성 요구
- 결과 확인 방법

AI는 이 설명을 Python과 Selenium WebDriver 코드로 바꾼다.

```text
자연어 Prompt
“로그인 후 OS Command Injection을 여러 번 검사해 줘”
        ↓
Cursor AI 또는 Continue
        ↓
Python·Selenium 코드 생성
        ↓
전문가가 오류와 위험한 동작 검토
        ↓
브라우저에서 코드 실행
        ↓
화면 Capture·Log·결과 파일 저장
```

### 사용한 도구

#### Cursor AI

AI 기능이 포함된 Code Editor다. 논문에서는 자연어 Prompt로 Selenium 점검 코드를 만들고 수정하는 데 사용한다.

#### Continue

Visual Studio Code에 설치하는 AI Coding Extension이다. OpenAI, Anthropic Claude, Mistral, Llama 등 다양한 Model을 연결할 수 있다고 설명한다.

논문은 두 도구를 사용했다고 밝히지만, 실제 실험에 사용한 정확한 Model 이름, Model Version, Temperature와 전체 Prompt 집합은 공개하지 않는다. 따라서 같은 결과를 완전히 재현하기 어렵다.

#### Selenium WebDriver

실제 Browser를 코드로 조종하는 자동화 도구다.

```text
Browser 실행
    ↓
URL 접속
    ↓
ID·Password Field 찾기
    ↓
값 입력
    ↓
Login Button 클릭
    ↓
취약점 검사 Page 이동
    ↓
Payload 입력
    ↓
화면 요소와 결과 확인
```

`requests`, `beautifulsoup4`, `sqlmap API`, Capture 도구와 보고서 Template Engine도 의존성 후보로 언급하지만, 각 도구가 실험에서 실제로 어느 정도 사용되었는지는 명확하지 않다.

### SQL Injection 코드 예시

논문은 다음 Prompt를 예로 든다.

```text
셀레니움을 이용해 사이트에 접속한 후,
id, pw 입력 칸에 SQL Injection 테스트 하는 코드 생성
```

생성된 코드는 세 가지 Payload를 준비하고 Login Field에 입력한다.

```text
' OR '1'='1
' UNION SELECT username, password FROM users--
admin'--
```

그다음 `welcome-message`라는 HTML 요소가 나타나는지를 최대 3초간 기다린다.

```text
welcome-message 발견
└─ 코드가 “취약점 발견” 출력

요소를 찾지 못함 또는 다른 예외 발생
└─ 코드가 “안전” 출력
```

### 코드 예시의 중요한 한계

이 예시는 이해하기 쉽지만 그대로 범용 취약점 판정기로 사용할 수는 없다.

1. `welcome-message`라는 ID는 특정 Test Site에만 존재한다.
2. 로그인 성공이 SQL Injection 때문인지 정상 인증이나 Session 재사용 때문인지 추가 검증하지 않는다.
3. `except:`가 모든 오류를 잡으므로 Browser 오류, Timeout과 Element 이름 오류도 “안전”으로 표시할 수 있다.
4. Payload마다 `refresh()`만 수행하므로 Site에 따라 Session과 입력 상태가 초기화되지 않을 수 있다.
5. 공격 전 정상 입력을 보내 비교하는 Negative Control이 없다.
6. 응답 본문, Status Code, DB 변화와 실제 권한 상승을 교차 검증하지 않는다.

따라서 이 코드는 AI 코드 생성 가능성을 보여주는 예시이지, 일반 웹사이트에서 SQL Injection을 정확히 검증하는 완성된 Scanner는 아니다.

### 로그인 후 OS Command Injection Prompt

Continue 실험에서는 URL, Login Field 이름, 계정값, 이동할 경로와 공격할 Field 이름을 자연어로 자세히 제공한다.

```text
로그인 URL과 계정정보
    ↓
로그인 Field와 값
    ↓
검사 Page 경로
    ↓
OS Command Injection 대상 Field
    ↓
여러 차례 실행하고 다시 Page로 이동
```

이는 RPA Diagram으로 작성하던 절차를 자연어 Prompt로 바꾸려는 시도다. 다만 최초 생성 코드는 사용자의 의도와 다르게 동작하거나 오류가 발생하여, 전문가가 추가 Prompt로 수정해야 했다고 논문이 직접 설명한다.

### 점검 범위를 단순 작업으로 제한한 이유

논문은 현재 단계에서는 복잡한 점검을 AI에 자세히 설명하는 것보다 사람이 직접 수행하는 편이 더 빠를 수 있다고 인정한다. 따라서 다음과 같은 반복적이고 단순한 작업에 우선 적용한다.

- 로그인 자동화
- 정해진 Field에 Payload 반복 입력
- Page 이동과 Button 클릭
- 취약점이 발견되지 않은 항목의 증적 생성
- 화면 Capture와 파일명 정리
- 정기 점검 코드의 재사용

이 제한은 AI가 전문가를 대체하는 것이 아니라 반복 작업을 보조한다는 뜻이다.

### 논문이 비교한 기존 방식

논문의 표 3은 웹 Scanner와 RPA를 다음과 같이 비교한다.

| 구분 | 웹 Scanner | RPA |
|---|---:|---:|
| Option 설정 시간 | 5분 이내 | 약 2시간 |
| 점검 속도 | 약 10분 | 약 10분 |
| 오탐률 | 10% | 0% |
| 설정 항목 수 | 10개 이내 | 약 50개 |
| 인증 처리 | 제한적 | 가능 |
| 비즈니스 Logic 탐지 | 어려움 | 용이 |

그러나 이 표의 숫자는 이번 코드 생성 AI 실험에서 모두 직접 측정한 것이 아니다.

- 선행연구의 74개 홈페이지 결과에서 SQL Injection과 OS Command Injection 관련 값을 정리했다고 설명한다.
- 오탐률 각주에서는 Broken Crystals와 DVWA를 대상으로 한 상용 Scanner Benchmark도 참고한다.
- 서로 다른 자료에서 가져온 값이 섞여 있으므로 동일 환경에서 세 방법을 엄격하게 비교한 표로 보면 안 된다.

### 코드 생성 AI와 기존 방식 비교

논문의 표 8은 다음과 같이 주장한다.

| 구분 | 웹 Scanner/RPA | 코드 생성 AI |
|---|---|---|
| 오탐률 | 10%/0% | 0%, 자동 제거 |
| 인증 | Session Update | 자동 로그인 가능 |
| 기능 탐지 | 어렵거나 직접 정의에 시간 필요 | 자동 기능 분석 |
| 유지보수 | 높음 | 낮음, 자동 반영 |
| 점검 속도 | 약 10분 | 약 10분 |
| 제품 비용 | 제품별 비용 발생 | 낮음, Open Source |
| Capture 관리 | 반자동 | 자동화 가능 |

이 표 역시 논문의 제안과 관찰을 정리한 성격이 강하다. 특히 `오탐률 0%`, `자동 기능 분석`, `유지보수 자동 반영`을 뒷받침하는 다음 정보가 없다.

- 전체 Test Case 수
- 실제 취약점 정답표
- TP·TN·FP·FN
- Precision·Recall·F1-score
- 여러 Model과 반복 실행의 평균·편차
- AI가 생성한 오류 코드의 비율
- 전문가 수정 전후 결과

따라서 `코드 생성 AI의 오탐률이 0%로 증명되었다`고 보고서에 쓰면 안 된다.

### 시간 단축 수치 검토

논문은 두 가지 시간 표현을 사용한다.

#### 본문의 사례

```text
코드 생성 AI 방법: 약 20분
웹 Scanner와 수동 점검 방법: 약 1시간
```

이를 그대로 계산하면 다음과 같다.

```text
(60분 - 20분) / 60분 × 100
= 약 66.7% 단축
```

#### 초록과 결론

```text
기존 방식 대비 약 40% 단축
```

본문의 20분 대 1시간과 결론의 40%는 계산상 일치하지 않는다. 40% 수치의 별도 평균표, 반복 횟수와 원자료가 제시되지 않아 어느 값이 최종 실험 결과인지 확인하기 어렵다.

따라서 정확한 보고서 표현은 다음과 같다.

> 논문은 결론에서 점검 시간이 약 40% 단축되었다고 주장한다. 다만 본문의 사례는 약 20분 대 1시간으로 제시되어 단순 계산 시 약 66.7% 단축에 해당하며, 두 수치가 일치하지 않고 세부 원자료도 제시되지 않는다.

### 정적 분석과 동적 분석 결합 주장 검토

초록에서는 기존 정적 분석과 동적 분석을 결합했다고 설명한다. 그러나 본문에서 구체적으로 구현하고 보여준 내용은 주로 다음과 같다.

- Selenium Browser 자동화
- SQL Injection·OS Command Injection Payload 실행
- 로그인과 Page 이동
- 화면 Capture와 증적 관리
- AI가 생성한 코드의 전문가 수정

소스코드 AST, 데이터 흐름, 위험 함수 추적과 같은 SAST 구현이나 정적 분석 결과를 Selenium Test에 전달하는 구체적인 Pipeline은 제시하지 않는다. 따라서 실제 구현은 `코드 생성 AI가 만든 Selenium 기반 DAST·RPA 자동화`에 더 가깝다고 보는 것이 정확하다.

### Nuclei와 공통점

```text
자연어로 검사 목적 작성
        ↓
검사 정의 생성
        ↓
실제 Target에 요청
        ↓
응답을 기준으로 결과 판단
```

두 방식 모두 반복적인 보안 검사 절차를 재사용 가능한 형태로 만든다.

### Nuclei와 차이점

| 논문의 방법 | Nuclei `-ai` |
|---|---|
| Cursor·Continue가 Python Selenium 코드 생성 | ProjectDiscovery AI가 Nuclei YAML Template 생성 |
| 생성 코드가 Browser를 직접 제어 | Nuclei Engine이 Protocol Request 실행 |
| 코드마다 오류 처리·결과 판정 구현 필요 | Matcher·Extractor·Output 구조 재사용 |
| 화면 Capture와 업무 흐름 자동화에 적합 | HTTP·DNS·SSL 등 다중 Protocol 대량 검사에 적합 |
| 전문가가 Python 코드 검토·수정 | Template 검증과 Debug가 필요 |

Nuclei는 이미 다음 기능을 제공한다.

```bash
nuclei -u https://example.com -ai "Detect exposed stack traces"
```

따라서 `자연어로 검사 코드를 생성한다`는 아이디어만 Nuclei에 추가하면 기존 `-ai`와 겹친다.

### Nuclei 연구로 발전시킬 방향

이 논문의 약점은 AI가 코드를 생성한 이후 품질을 전문가가 수동으로 확인해야 한다는 점이다. Nuclei에서는 다음 연구로 차별화할 수 있다.

```text
자연어 Prompt
    ↓
AI Nuclei Template 생성
    ↓
위험한 Protocol·Payload·Target 범위 검사
    ↓
취약·정상·404·WAF Response Fixture 실행
    ↓
Matcher 오탐·미탐 자동 측정
    ↓
전문가 승인 후 실제 Target 실행
```

구체적인 기능 후보:

- AI 생성 Template 전용 Sandbox
- 위험한 Payload와 외부 Callback 사용 경고
- 정상 응답을 이용한 Negative Control
- AI 생성 코드·Template의 Model과 Prompt 기록
- 생성 전후 Diff와 전문가 수정 이력
- Fixture 기반 Template Robustness Test
- 같은 Prompt를 여러 번 실행해 결과 안정성 측정
- AI 설명과 Nuclei Matcher의 확정 결과 분리

### 보안상 주의점

- Prompt에 실제 ID, Password, Cookie와 Token을 그대로 넣지 않는다.
- AI가 생성한 공격 코드를 승인 없이 실행하지 않는다.
- 실제 운영 사이트가 아닌 허가된 Test 환경에서 먼저 실행한다.
- 무한 반복, 파일 삭제, 데이터 변경과 과도한 Payload를 검사한다.
- 외부 AI Service를 사용하면 Source Code와 인증정보 전송 범위를 확인한다.
- 생성된 Test 결과가 “안전”이라고 출력해도 Timeout이나 코드 오류인지 구분한다.

### 연구 한계

- 실험 Target과 전체 Test Case 수가 명확하게 공개되지 않았다.
- Cursor와 Continue에 연결한 정확한 AI Model과 Version이 없다.
- 생성 코드의 성공률과 전문가 수정 횟수가 정량화되지 않았다.
- 오탐률 0% 주장에 필요한 Confusion Matrix가 없다.
- 40% 시간 단축 주장과 본문 20분 대 1시간 사례가 일치하지 않는다.
- SAST와 DAST를 결합한 구체적인 구현은 제시되지 않는다.
- 복잡한 비즈니스 Logic과 대규모 Menu는 여전히 수동 작업이 필요하다고 인정한다.
- 생성 AI가 학습하지 않은 최신 취약점과 특정 Framework에 약할 수 있다.

### 핵심 평가

이 논문의 실제 가치는 AI가 전문가를 대신해 새로운 취약점을 스스로 발견했다는 데 있지 않다.

```text
전문가가 알고 있는 점검 절차
        ↓ 자연어 Prompt
AI가 반복 가능한 Selenium 코드로 변환
        ↓
로그인·입력·Capture·증적 정리 자동화
        ↓
전문가는 복잡한 분석에 집중
```

따라서 이 연구는 `자연어 기반 보안 Test 자동화와 증적 생성`의 사례로는 유용하다. 반면 `새로운 취약점 자동 발견`, `오탐률 0%`, `정적·동적 분석 통합`의 성능을 강하게 입증한 연구로 인용하기에는 실험 정보가 부족하다.

### 연구 목적

논문은 당시 Nikto와 같은 룰 기반 웹 취약점 분석 도구가 가진 두 가지 문제를 지적한다.

```text
기존 룰 기반 분석
    ↓
룰 DB의 모든 고정 경로를 대상 서버에 요청
    ↓
1. 대상 사이트가 작아도 모든 룰을 실행해 시간이 낭비됨
2. 경로가 다르거나 이름만 같은 다른 프로그램을 잘못 판단함
```

첫 번째는 효율성 문제다. 대상 서버의 페이지 수나 실제 설치 프로그램과 상관없이 룰 DB의 모든 규칙을 실행하므로, 룰이 늘어날수록 요청 수도 계속 증가한다.

두 번째는 정확성 문제다. 기존 도구는 특정 파일 경로와 응답 문자열을 중심으로 판단한다. 취약한 프로그램이 다른 경로에 설치되면 놓칠 수 있고, 반대로 이름이 같은 파일이지만 전혀 다른 프로그램이면 취약한 것으로 잘못 판단할 수 있다.

### 기존 방식에서 발생하는 두 가지 오류

#### 시나리오 1: 설치 경로가 달라 생기는 미탐

룰에는 취약한 웹 메일 파일의 경로가 다음처럼 저장되어 있다고 가정한다.

```text
/webmail/mail_read.php
```

하지만 실제 서버에서는 같은 취약한 웹 메일 프로그램이 다른 디렉터리에 설치될 수 있다. 고정 경로만 요청하면 `404 Not Found`가 반환되고, 기존 도구는 해당 프로그램이 없다고 판단한다. 실제 취약한 프로그램은 다른 경로에 존재하지만 검사가 그 위치까지 도달하지 못하므로 이는 미탐이다.

#### 시나리오 2: 파일 이름만 같아 생기는 오탐

룰이 취약한 웹 메일 프로그램의 `read.cgi`를 알고 있더라도, 대상 서버의 `read.cgi`가 회사 인트라넷 공지사항을 읽는 전혀 다른 파일일 수 있다.

```text
룰 DB의 read.cgi
└─ 웹 메일 읽기 기능

대상 서버의 read.cgi
└─ 사내 공지사항 읽기 기능
```

고정 경로와 파일 이름만 비교하면 두 파일을 같은 프로그램으로 착각하고, 취약하지 않은 다른 프로그램에 취약점이 있다고 판단할 수 있다. 이는 오탐이다. 이 논문의 핵심은 이름뿐 아니라 페이지 안의 특징을 함께 비교하자는 것이다.

### WAVE가 비교하는 웹 페이지 특성

논문은 취약점이 보고된 동적 페이지가 단순한 글자만 가진 문서가 아니라 프로그램의 기능을 드러내는 여러 요소를 가진다고 본다.

| 특성 | 의미 | 비교하는 이유 |
|---|---|---|
| JavaScript 함수 이름 | 페이지에서 정의하거나 호출하는 함수 이름 | 같은 프로그램의 페이지는 비슷한 함수 구조를 가질 가능성이 있음 |
| 프로그램 변수 | GET·POST에 사용하는 타입과 변수 이름 | 같은 기능이면 입력 매개변수 구성이 유사할 수 있음 |
| Link 태그 | `href`에 들어 있는 하이퍼링크 값 | 페이지 사이의 연결 구조를 비교할 수 있음 |
| `img` 태그 | 이미지 파일의 경로와 이름 | 프로그램별 화면 자원의 특징이 나타날 수 있음 |

이 네 종류의 값을 여기서는 [[05_논문 전용 용어 사전#^term-feature-information|특성 정보]]라고 부른다.

```text
취약점 DB의 알려진 취약 페이지
    ↓ JavaScript·변수·링크·이미지 특성 추출
특성 집합 A

대상 서버에서 찾은 같은 이름의 페이지
    ↓ 같은 종류의 특성 추출
특성 집합 B

A와 B 비교
    ↓
같은 프로그램의 페이지인지 판단
```

### WAVE 전체 처리 흐름

논문 그림 6의 절차는 다음 세 단계로 정리할 수 있다.

```text
1. 사이트 구조 및 데이터 추출
   └─ 대상 사이트를 탐색하고 페이지와 특성 정보를 모음
        ↓
2. 룰 DB와 파일 이름·콘텐츠 특성 비교
   └─ 취약점이 알려진 페이지와 같은 종류인지 확인
        ↓
3. 취약한 요청 전송 및 응답 분석
   └─ 관련성이 확인된 페이지에만 취약점 룰을 적용
        ↓
최종 취약점 결과
```

중요한 점은 콘텐츠 유사도만으로 취약점을 확정하지 않는다는 것이다. 유사도 비교는 “이 룰을 적용할 대상이 맞는가?”를 먼저 확인하는 단계다. 그 다음에 기존 룰 기반 요청과 응답 분석을 실행해 실제 취약 여부를 판단한다.

### 효율성 평가

기존 Nikto 방식의 시간 복잡도는 룰 DB에 들어 있는 모든 규칙을 실행하는 형태로 표현한다.

```text
Nikto 방식
룰 약 3,300개 × 각 요청의 응답 시간
```

WAVE 방식은 다음 비용을 합친다.

```text
대상 서버의 전체 페이지 탐색·DB 조회 비용
    +
취약 페이지로 추정된 일부 페이지의
특성 비교 시간과 HTTP 응답 시간
```

그림 7은 다음 조건을 이용한 계산 결과다.

- 룰 DB: 약 3,300개
- 대상 서버 규모: 그래프상 약 1~1,960페이지
- 전체 페이지 중 취약 페이지 비율: 10%와 20%
- Nikto 분석 시간: 그래프상 약 310,000ms로 일정
- WAVE 10% 조건: 약 248,000ms에서 시작하여 약 298,000ms까지 증가
- WAVE 20% 조건: 약 249,000ms에서 시작하여 약 347,000ms까지 증가

작은 사이트에서는 WAVE가 전체 3,300개 룰을 모두 보내지 않아 더 빠르게 계산된다. 하지만 사이트가 커지거나 검사할 취약 후보 페이지 비율이 20%처럼 높아지면, 사이트 탐색과 특성 비교 비용이 늘어 Nikto보다 느려질 수도 있다.

> [!warning] 그래프를 읽을 때 주의할 점
> 논문은 이를 시간 복잡도로 계산한 선형 결과라고 설명한다. 여러 실제 사이트를 반복 스캔해 평균·표준편차를 구한 실측 성능표가 아니다. 따라서 “WAVE가 항상 몇 % 빠르다”고 결론 내릴 수 없다.

### 정확성 평가

정확성 평가는 이름은 같지만 서로 다른 웹 게시판 프로그램의 페이지 두 개로 진행했다.

| 페이지 | 프로그램 | 사이트 |
|---|---|---|
| `board.php` | pico 보드 | picomax.net |
| `board.php` | 그누 보드 | sir.co.kr |

기존 룰 기반 방식은 파일 이름이 같기 때문에 두 페이지에 같은 규칙을 적용하여 두 경우를 모두 취약하다고 판단했다.

WAVE는 먼저 콘텐츠 특성을 비교하여 pico 보드와 그누 보드가 서로 다른 프로그램임을 구분했다. 그 후 해당하는 HTTP 요청을 전송한 결과, 그누 보드에 취약점이 있다는 결과를 얻었다고 보고한다.

```text
기존 방식
board.php라는 이름이 같음
    ↓
두 페이지 모두 취약하다고 판단

WAVE
board.php 이름 확인
    ↓
JavaScript·변수·링크·이미지 특성 비교
    ↓
프로그램 종류 구분
    ↓
해당 룰 실행
    ↓
그누 보드만 취약하다고 판단
```

> [!warning] 정확도 수치의 한계
> 논문에는 이 사례에 대한 TP·TN·FP·FN 수, 전체 시험 페이지 수, 반복 횟수, 정확도·정밀도·재현율이 제시되지 않는다. 따라서 이 한 사례를 근거로 WAVE의 전체 오탐률이나 정확도를 숫자로 말하면 안 된다.

### Nuclei와의 공통점

WAVE와 Nuclei는 모두 검사 엔진과 외부에 저장된 규칙을 분리한다.

```text
WAVE
취약점 DB의 룰
    ↓
대상 페이지 확인
    ↓
HTTP 요청·응답으로 판정

Nuclei
YAML·JSON Template
    ↓
대상과 Template 선택
    ↓
Protocol 요청·Matcher로 판정
```

두 방식 모두 새로운 취약점을 추가할 때 엔진 전체를 다시 작성하지 않고 룰 또는 Template을 추가할 수 있다는 장점이 있다.

### Nuclei와의 차이점

| 비교 항목 | WAVE | Nuclei |
|---|---|---|
| 주요 대상 | 웹 애플리케이션 페이지 | HTTP·DNS·SSL·Network 등 |
| 규칙 저장 | 취약점 DB의 룰 | YAML·JSON Template |
| 사전 확인 | 페이지 콘텐츠 특성 유사도 | Template Filter, 기술 기반 자동 선택 등 |
| 탐색 | 사이트 구조와 페이지 데이터 추출 | 입력 대상 공급, HTTP·Headless 등 Template 실행 |
| 판정 | 관련 페이지 확인 후 룰 요청·응답 비교 | Matcher와 Extractor |
| 연구 시점 | 2008년의 프로토타입 | 현재 사용되는 오픈소스 스캐너 |

Nuclei의 `-as`는 Wappalyzer 기술 탐지 결과를 이용해 관련 태그의 Template을 선택한다. WAVE는 기술 이름보다 더 세부적으로 특정 페이지의 JavaScript 함수·변수·링크·이미지가 알려진 취약 페이지와 유사한지를 비교한다는 차이가 있다.

### Nuclei 연구에 활용할 수 있는 부분

WAVE의 핵심은 공격 룰을 실행하기 전에 “이 페이지가 정말 그 룰의 대상인가?”를 확인하는 사전 검증 단계다.

```text
Nuclei Template 선택
    ↓
대상 Response에서 제품·페이지 특징 추출
    ↓
Template이 기대한 제품·페이지와 일치하는지 점수화
    ↓
관련성이 충분할 때만 공격 Matcher 실행
```

이는 Nuclei의 오탐 감소 기능을 연구할 때 다음 아이디어로 발전시킬 수 있다.

- Custom 404 페이지와 실제 제품 페이지를 구분하는 사전 검사
- 제품명 하나가 아니라 DOM, JavaScript, 링크와 정적 자원 경로를 함께 이용한 Fingerprint
- Template마다 실행 전 필요한 페이지 특징을 Metadata로 정의
- 특징 일치 점수와 최종 Matcher 결과를 분리하여 보고
- 사전 필터로 줄인 HTTP 요청 수와 놓친 취약점 수를 함께 측정

### 연구의 한계

- 5쪽 분량의 학술발표 논문으로 구현 세부사항이 충분히 공개되지 않았다.
- 네 가지 특성을 어떤 수식이나 임계값으로 합치는지 구체적인 알고리즘이 없다.
- 효율성 그래프는 실제 반복 측정이 아니라 복잡도 계산에 기반한다.
- 정확성 평가는 `board.php` 두 사례 중심이며 전체 데이터셋이 없다.
- 오탐률·미탐률·정밀도·재현율과 같은 정량 지표가 없다.
- JavaScript가 동적으로 생성한 DOM이나 현대적인 SPA를 처리하는 방법은 다루지 않는다.
- 현재 실행 가능한 WAVE 소스코드나 공개 데이터셋이 제시되지 않는다.

### 핵심 평가

이 논문의 가치는 “콘텐츠가 비슷하면 취약하다”라고 판정한 데 있지 않다.

```text
고정 경로·파일 이름만 보는 기존 도구
        ↓
대상 페이지가 실제로 같은 프로그램인지 콘텐츠로 확인
        ↓
관련성이 확인된 곳에만 취약점 룰 실행
```

즉 룰 기반 스캐너 앞에 대상 적합성 확인 단계를 추가하여 불필요한 요청과 잘못된 룰 적용을 줄이려 한 초기 연구다. Nuclei 연구에서는 `Template 실행 전 콘텐츠 기반 적합성 검증`의 선행연구로 사용하는 것이 가장 적절하다.
