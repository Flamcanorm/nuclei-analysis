## 1. Bitscanner

### 연구 목적

웹 애플리케이션을 크롤링하고, 미리 정의한 30가지 공격 패턴으로 취약점을 빠르게 검사하는 자동 스캐너를 제안한다.

### 처리 흐름

```text
웹사이트 입력
    ↓
전체 깊이 크롤링
    ↓
페이지·Form·JSON·XML·AJAX 분석
    ↓
GET·POST 매개변수 추출
    ↓
공격 패턴을 매개변수에 삽입
    ↓
조작된 HTTP 요청 전송
    ↓
응답을 오류 패턴 DB와 비교
    ↓
취약점 보고서 생성
```

`매개변수`는 사용자가 서버에 전달하는 값이다.

```text
/user?id=10
       │  └─ 값
       └─ 매개변수 이름
```

Bitscanner는 이러한 값에 SQL Injection, XSS 등의 공격 문자열을 삽입하여 서버 반응을 확인한다.

### Nuclei와 공통점

```text
Bitscanner 공격 패턴 DB
≈ Nuclei Template

Bitscanner 응답 패턴 비교
≈ Nuclei Matcher

Bitscanner 보고서 생성
≈ Nuclei Output Writer
```

두 프로그램 모두 외부에서 요청을 보내고 응답이 미리 정의한 조건과 일치하는지 검사한다.

### 차이점

- Bitscanner는 웹사이트를 직접 크롤링하고 입력 매개변수를 자동 탐색한다.
- Nuclei는 Template에 정의된 경로와 요청을 실행하는 방식이 중심이다.
- Nuclei는 HTTP뿐 아니라 DNS, SSL, TCP, Headless, Cloud 등도 지원한다.
- Bitscanner는 논문 기준 30개 취약점 유형에 집중한다.

### 실험 결과

- 87개의 웹 애플리케이션을 검사했다.
- 3개의 웹 애플리케이션에서 Acunetix·Arachni와 속도를 비교했다.
- 논문은 오탐률 0%라고 주장한다.
- PDF, XML, HTML, CSV 및 대시보드 보고서를 제공한다.

### 한계

오탐률 0%라는 수치는 다음 사항을 확인한 후 받아들여야 한다.

- 실제 취약점의 정답을 누가 결정했는가?
- 전문가가 모든 결과를 수동으로 검증했는가?
- 실험 대상이 공개되지 않아 재현이 어렵다.
- 속도 비교 대상이 3개로 적다.
- 결과가 30개 취약점 유형에 한정된다.

## 2. 홈페이지의 웹취약점분석모델에 관한 실증적 연구

### 연구 목적

단순히 발견된 취약점 개수만 세는 방식에서 벗어나, 홈페이지 제작 형태와 정보보안 요소의 관계를 함께 분석하는 모델을 제안한다.

### 처리 흐름

```text
홈페이지 운영환경 확인
    ↓
자체 제작 또는 CMS 종류를 7가지로 분류
    ↓
점검 대상 기능과 경로 결정
    ↓
취약점을 3가지 기준으로 분류
├─ 기술 기준
├─ 관리 기준
└─ 인증 기준
    ↓
자동 점검
    ↓
수동 점검으로 오탐 제거
    ↓
PoC로 실제 취약점 확인
    ↓
기밀성·무결성·인증성과의 관계 분석
```

### 주요 결과

자동 점검 결과를 수동으로 다시 검증했을 때 다음 비율로 취약점이 확인되었다.

- SQL Injection: 약 50%
- XSS: 약 90%

자동 도구가 출력한 결과가 모두 실제 취약점은 아니라는 사실을 보여준다.

### Nuclei 관련성

```text
Nuclei 탐지 결과
    ↓
AI 또는 사람의 추가 검증
    ↓
실제 취약 가능성 분석
    ↓
사람이 최종 판단
```

Nuclei 결과에 AI 분석을 추가해야 하는 연구 배경으로 활용할 수 있다.

### 한계

- 중소기업 홈페이지 중심이다.
- 홈페이지 제작 형태와 CMS 분석이 중심이다.
- 새로운 취약점 탐지 알고리즘은 제안하지 않는다.
- 복잡한 취약점은 여전히 컨설턴트의 경험에 영향을 받는다.

## 3. AI 기반 보안 취약점 탐지 시스템

### 연구 목적

고정 규칙을 사용하는 OWASP ZAP의 한계를 머신러닝으로 보완하려는 연구다.

### 처리 흐름

```text
데이터 수집
├─ CWE 데이터
├─ OWASP ZAP 로그
├─ GitHub 저장소
└─ 실시간 보안 이벤트 로그
    ↓
전처리
├─ 노이즈 제거
├─ 정상·공격 레이블 부착
└─ SMOTE로 데이터 불균형 보완
    ↓
학습 데이터 80%
테스트 데이터 20%
    ↓
Random Forest 학습
    ↓
Kafka를 통한 실시간 처리
    ↓
정상 또는 취약 요청 예측
```

### SMOTE

정상 데이터보다 공격 데이터가 지나치게 적으면 AI가 대부분의 입력을 정상으로 판단할 수 있다.

SMOTE는 적은 쪽의 데이터를 참고하여 인공 학습 데이터를 추가하는 기법이다.

### 결과

- AI 평균 정확도: 91%
- OWASP ZAP 대비 정확도: 약 6% 향상
- AI 오탐률: 10%
- OWASP ZAP 오탐률: 12%
- AI 미탐률: 12.5%
- OWASP ZAP 미탐률: 14%
- AI 평균 탐지 시간: 9초
- OWASP ZAP 평균 탐지 시간: 10초
- AI F1-score: 0.91
- OWASP ZAP F1-score: 0.87

### 중요한 한계

AI와 OWASP ZAP을 동일한 시험 환경에서 비교하지 않았다.

```text
OWASP ZAP
└─ OWASP Benchmark의 기존 결과 사용

AI 시스템
└─ 별도로 전처리한 데이터셋 사용
```

서로 다른 시험지의 점수를 비교한 것과 비슷하므로, AI가 반드시 6% 우수하다고 확정하기 어렵다.

그 밖의 한계는 다음과 같다.

- SQL Injection, XSS, CSRF 중심이다.
- RCE, 경로 조작, 역직렬화 등은 충분히 다루지 못했다.
- 새로운 환경에서의 일반화 성능을 검증하지 못했다.
- 모델 업데이트가 수동이다.
- 실제 대규모 네트워크의 실시간 성능을 충분히 검증하지 못했다.

## 4. 정적·동적 분석 크로스 체크

### 연구 목적

정적 분석과 동적 분석 결과를 교차 검증하여 오탐·미탐·과탐을 줄이고, 탐지 정확도를 포함한 애플리케이션 위험도를 계산한다.

### 처리 흐름

```text
소스코드 정적 분석
    ↓
의심되는 취약점 발견
    ↓
맞춤형 정적 분석 규칙 생성
    ↓
Exploit 코드 생성
    ↓
실행 중인 애플리케이션에 동적 검증
    ↓
두 분석 결과 크로스 체크
    ↓
취약점 정확도와 위험도 계산
```

### Nuclei 관련성

```text
SAST가 소스코드에서 의심 지점 발견
    ↓
해당 지점을 검사하는 Nuclei Template 실행
    ↓
실제 응답에서 취약점 재검증
```

### 결과와 한계

- CWE/SANS Top 25 중 상위 10개 항목을 기준으로 비교했다.
- 정적·동적 분석을 결합한 프로토타입을 구현했다.
- 기존 도구보다 전반적으로 많은 정탐을 보였다.
- CWSS 위험도와 탐지 정확도를 결합했다.
- 일부 항목에서는 탐지 수 증가와 함께 오탐 수도 증가했다.

더 많이 탐지했다는 사실만으로 모든 결과가 정확하다는 뜻은 아니다.

## 5. LSTM 기반 HAST 아키텍처

### 연구 목적

```text
SAST
소스코드 검사
     ↘
      HAST
     ↗
DAST
실행 중인 애플리케이션 검사
     +
LSTM
HTTP 요청 시퀀스 분석
```

SAST, DAST와 LSTM을 하나의 보안 파이프라인으로 결합하는 아키텍처를 제안한다.

### LSTM을 사용하는 이유

LSTM은 데이터가 나타나는 순서와 앞뒤 관계를 학습한다.

```text
단순 문자열 검사
└─ 요청에 'select'라는 단어가 있는가?

LSTM 분석
└─ 단어·기호·값이 어떤 순서와 관계로 나타나는가?
```

긴 Payload나 여러 요청의 연속적인 특징을 분석하는 데 활용할 수 있다.

### 제안 내용

- HTTP 요청과 Payload를 LSTM으로 분석한다.
- SAST와 DAST 결과를 통합한다.
- 새로운 데이터로 재학습할 수 있다.
- CI/CD 파이프라인과 연결한다.
- 개발부터 운영까지 전 주기 검사를 목표로 한다.

### 가장 중요한 한계

실제 구현과 정량적인 성능 실험을 수행하지 않은 설계 제안 연구다.

- 정확도와 오탐률 측정이 없다.
- LSTM과 다중 분석으로 연산 비용이 커질 수 있다.
- 실제 지연 시간과 처리량 검증이 필요하다.

이 논문은 성능 증거보다 시스템 구조 참고자료로 사용하는 것이 적절하다.

## 6. 웹사이트 구조화 및 페이지별 동작크기

### 연구 목적

- 검사하지 않은 페이지 발생
- 점검자가 기능을 빠뜨리는 문제
- 점검자마다 검사 범위가 달라지는 문제
- 검사 기간을 객관적으로 계산하기 어려운 문제

이러한 수동 동적 점검의 문제를 줄이는 것이 목적이다.

### 제안 방법

```text
웹사이트의 정보구조 IA 작성
    ↓
세부 페이지 식별
    ↓
페이지를 7가지 동작 기능으로 분류
    ↓
페이지의 매개변수 수 확인
    ↓
페이지별 동작크기 SoA 계산
    ↓
전체 웹사이트 점검 규모 계산
    ↓
하루 점검 가능량과 전체 기간 산정
```

SoA는 페이지를 검사하는 데 필요한 작업량을 나타내는 값이다. 이 논문에서는 주로 매개변수 개수를 사용한다.

### Nuclei 관련성

Nuclei에 다음과 같은 검사 범위 보고 기능을 추가할 때 활용할 수 있다.

```text
전체 발견 엔드포인트
실제로 검사한 엔드포인트
검사하지 못한 엔드포인트
각 엔드포인트에 적용한 템플릿
```

### 한계

- 수동 점검 중심이다.
- 매개변수 개수만으로 작업량을 계산한다.
- 매개변수별 중요도를 반영하지 않는다.
- 취약점 판정 알고리즘을 개선하는 연구는 아니다.

## 7. 웹 애플리케이션 보안 취약점 진단 방법 개선

### 연구 목적

자동 정적 분석과 동적 진단에서 발생하는 오탐·미탐을 줄이기 위해, 소스코드 문맥을 수동으로 확인한 뒤 의심되는 부분만 동적으로 검증한다.

### 제안 흐름

```text
소스코드 수동 정적 분석
    ↓
취약 가능성이 있는 코드 확인
    ↓
실제로 실행되는 코드인지 확인
    ↓
해당 기능만 동적 검사
    ↓
실제 취약점으로 확인
```

### 실험 대상

2개 사이트에서 다음 4개 항목을 검사했다.

- SQL Injection
- XSS
- 위험한 파일 업로드
- 주요 파일 다운로드

자동 정적 분석 도구는 주석 처리된 코드나 실행되지 않는 코드까지 탐지해 오탐을 만들 수 있었다. 제안 방법은 데이터 흐름과 코드 문맥을 사람이 확인하여 실제 취약점을 더 많이 찾았다.

### Nuclei와 차이점

- 소스코드 접근이 필요하다.
- 수동 정적 분석이 중심이다.
- 외부 요청만 사용하는 순수 블랙박스 검사가 아니다.
- 기존 방법보다 검사 시간이 더 필요하다.

### AI 관련성

논문은 다음 방향을 향후 연구로 제시한다.

```text
단순한 코드 패턴
    ↓
데이터 문맥과 상관관계 분석
    ↓
AI를 이용한 오탐·미탐 감소
```

AI 시스템을 실제로 구현한 논문은 아니므로, AI의 효과를 증명한 연구로 인용하면 안 된다.
