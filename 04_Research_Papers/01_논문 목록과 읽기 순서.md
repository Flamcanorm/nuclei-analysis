### 1. Nuclei와 비슷한 자료

다음 자료는 `검사 규칙을 불러오고 → 대상에 요청을 보내고 → 응답 조건으로 결과를 판단한다`는 흐름을 Nuclei와 비교하기 좋다.

> [!note] RESTler의 위치
> RESTler도 자동으로 요청을 만들고 응답을 검사한다. 하지만 범용 Template Scanner보다는 `REST API 요청 순서와 상태 관계`에 집중하므로, Nuclei 유사 자료이면서 상태 기반 기능 아이디어 자료로 보는 것이 적절하다.

### 2. 기능을 추가할 때 참고할 자료

> [!info] 자료 종류 표시
> **[국내 논문]** 국내 학술지·학위논문 · **[해외 논문]** 해외 학회·학술지 논문 · **[오픈소스]** 공개된 실제 프로그램 또는 Rule 저장소 · **[해외 논문+오픈소스]** 논문과 실행 가능한 공개 코드가 모두 있는 자료

#### 오탐을 줄이고 싶을 때

- **[국내 논문] WAVE:** Rule 실행 전에 대상 페이지가 실제로 관련 프로그램인지 확인한다.
- **[국내 논문] 정적·동적 크로스 체크:** 한 분석의 결과를 다른 방법으로 다시 검증한다.
- **[국내 논문] 홈페이지 웹취약점분석모델:** 자동 결과를 사람이 최종 검증한다.
- **[오픈소스] Semgrep Rules:** 정상·취약 예제로 Rule 자체를 시험한다.

#### 검사하지 못한 영역을 보여주고 싶을 때

- **[해외 논문] State of the Krawlers:** Crawler가 실제로 방문한 범위를 측정한다.
- **[해외 논문+오픈소스] Black Widow:** JavaScript Event와 로그인 후 상태를 따라간다.
- **[국내 논문] 웹사이트 구조화 연구:** 페이지와 기능 단위로 검사 범위를 나눈다.
- **[해외 논문] MLLM Crawler:** 화면과 DOM을 AI가 해석해 다음 행동을 고른다.

#### 이전 결과를 다음 검사에 사용하고 싶을 때

- **[해외 논문+오픈소스] RESTler:** 앞 요청에서 생성된 ID를 다음 요청에 사용한다.
- **[오픈소스] BBOT:** 한 Module의 결과를 다른 Module의 입력으로 전달한다.
- **[해외 논문] Spider-Scents:** 여러 요청으로 발생한 DB 상태 변화를 추적한다.

#### AI 기능을 만들고 싶을 때

- **[해외 논문+오픈소스] PentestGPT:** 계획, 명령 생성, 결과 해석을 분리한다.
- **[오픈소스] CAI:** Agent가 사용할 Tool과 금지할 행동을 Guardrail로 관리한다.
- **[국내 논문] AI 기반 동적 분석:** 기존 Rule 결과를 ML로 보조 분류한다.
- **[국내 논문] 코드 생성 AI 연구:** 자연어 점검 절차를 Selenium Code로 바꾼다.

### 3. 성능을 평가할 때 참고할 자료

| 평가하려는 것 | 국내 자료 | 해외 자료·오픈소스 |
|---|---|---|
| 검사한 페이지와 놓친 영역 | **[국내 논문]** 웹사이트 구조화 | **[해외 논문]** State of the Krawlers |
| 오탐·미탐 감소 | **[국내 논문]** 홈페이지 분석모델, 정적·동적 크로스 체크 | - |
| 요청 수와 실행 시간 | **[국내 논문]** WAVE, Bitscanner | - |
| AI 방법의 실험 근거 | **[국내 논문]** AI 동적 분석, 코드 생성 AI, LSTM HAST | - |

> [!warning] 평가 자료를 읽을 때
> 논문이 제시한 숫자가 실제 반복 측정인지, 계산으로 만든 그래프인지, 전체 Test Case 수가 공개되었는지 확인해야 한다. 예를 들어 WAVE의 효율성 그래프는 실측 Benchmark가 아니라 복잡도 계산이며, LSTM HAST는 실제 구현 없이 구조를 제안한 연구다.

### 정리

```text
Nuclei 구조를 설명
└─ Bitscanner·WAVE·Jaeles·Nmap NSE·Tsunami·OpenVAS

추가 기능을 설계
└─ 만들 기능에 맞는 논문과 오픈소스를 선택

기능을 평가
└─ 오탐·미탐·Coverage·요청 수·시간을 측정
```

WAVE나 RESTler처럼 두 용도로 사용할 수 있는 자료도 있다. 이 경우 보고서에서 `Nuclei와 어떤 점이 비슷한지`와 `어떤 기능 아이디어를 얻었는지`를 문장을 나누어 설명하면 된다.

## 추가로 찾은 해외 논문

아래 자료는 처음 확보한 7편과 중복되지 않는다. 제목을 누르면 원문 또는 공식 발표 페이지로 이동한다.

### 8. Black Widow: Blackbox Data-driven Web Scanning

- 발표: IEEE Symposium on Security and Privacy, 2021
- 분야: 블랙박스 웹 크롤링, JavaScript 이벤트, 상태 의존성, XSS
- Nuclei 관련성: 높음
- 원문: [Black Widow 논문](https://www.cse.chalmers.se/~andrei/bw21.pdf)
- 코드: [SecuringWeb/BlackWidow](https://github.com/SecuringWeb/BlackWidow)
- 상세 분석: [[02_논문별 상세 분석#8. Black Widow: Blackbox Data-driven Web Scanning]]

### 9. RESTler: Stateful REST API Fuzzing

- 발표: ICSE, 2019
- 분야: OpenAPI, 상태 기반 API Fuzzing, 요청 의존성
- Nuclei 관련성: 매우 높음
- 코드와 논문 안내: [Microsoft RESTler](https://github.com/microsoft/restler-fuzzer)
- 상세 분석: [[02_논문별 상세 분석#9. RESTler: Stateful REST API Fuzzing]]

### 17. 코드 생성 AI를 이용한 웹 취약점 점검 방법에 관한 연구

- 영문 제목: `A Study on Web Vulnerability Assessment Methods Using Code Generation AI`
- 저자: 박영식·윤종필·현선진·임종태
- 게재: 한국차세대컴퓨팅학회 논문지, 제21권 제4호, 20~30쪽
- 투고: 2025년 3월 18일
- 심사: 2025년 3월 23일
- 게재 확정: 2025년 8월 18일
- DOI: [10.23019/kingpc.21.4.202508.002](https://doi.org/10.23019/kingpc.21.4.202508.002)
- 실제 구현 중심: Cursor·Continue를 이용한 Python·Selenium 점검 코드 생성
- 분야: Code Generation AI, Selenium, RPA 대체, 동적 웹 취약점 점검, 증적 자동화
- Nuclei 관련성: 매우 높음
- 상세 분석: [[02_논문별 상세 분석#17. 코드 생성 AI를 이용한 웹 취약점 점검 방법]]

> [!warning] 실험 수치 해석
> 논문은 결론에서 점검 시간이 `약 40% 단축`되었다고 주장한다. 그러나 본문에는 코드 생성 AI 약 20분, 기존 방식 약 1시간이라고 적혀 있어 단순 계산하면 약 66.7% 단축이다. 또한 `오탐률 0%`를 제시하지만 TP·TN·FP·FN, 전체 Test Case 수와 반복 실험 원자료가 없다.

> [!note] 실제 구현 범위
> 초록은 정적·동적 분석 결합을 설명하지만 본문에서 구체적으로 보여준 구현은 Selenium Browser 자동화, SQL·OS Command Injection Payload 실행, 로그인, 화면 Capture와 전문가의 생성 코드 수정이다. 따라서 현재 증거만 보면 `AI가 생성한 Selenium 기반 DAST·RPA 자동화`에 더 가깝다.

### 18. 웹 애플리케이션 취약점 분석 시스템

- 영문 제목: `Web Application Vulnerability Analyzing System`
- 저자: 이동건·이민수·조상현·차성덕
- 게재: 2008년 가을 학술발표논문집, Vol. 35, No. 2(D), 1~5쪽
- 제안 시스템: WAVE(Web Application Vulnerability Estimator)
- 분야: 블랙박스 웹 취약점 분석, 룰 기반 검사, 웹 페이지 콘텐츠 유사도
- 핵심 문제: 고정 경로만 확인하는 기존 룰 기반 도구의 오탐과 불필요한 요청
- 핵심 방법: 취약점이 알려진 페이지와 대상 서버 페이지의 콘텐츠 특징을 비교한 뒤, 같은 종류의 페이지라고 판단될 때만 취약점 룰을 적용
- Nuclei 관련성: 매우 높음
- 원문 정보: [DBpia](https://www.dbpia.co.kr/journal/articleDetail?nodeId=NODE01074718)
- 상세 분석: [[02_논문별 상세 분석#18. 웹 애플리케이션 취약점 분석 시스템]]

> [!warning] 실험 수치 해석
> 효율성 그래프는 실제 여러 서버를 반복 측정한 결과가 아니라, 룰 3,300개와 페이지 수·취약 페이지 비율 10% 및 20%를 이용해 시간 복잡도를 계산한 선형 비교다. 정확성 실험도 이름이 같은 `board.php` 두 페이지를 비교한 소규모 사례이므로 전체 정확도나 오탐률 수치로 일반화하면 안 된다.
