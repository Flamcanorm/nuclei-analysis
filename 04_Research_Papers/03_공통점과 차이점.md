## 공통점

모든 논문은 기존 진단 방식 하나만으로 정확한 결과를 얻기 어렵다는 문제에서 시작한다.

```text
하나의 분석 방식
    ↓
오탐·미탐·누락·시간 문제 발생
    ↓
추가 정보나 다른 분석 방법 결합
    ↓
정확도·신뢰성·효율 향상 시도
```

각 연구가 선택한 해결 방법은 다음과 같다.

```text
Bitscanner
└─ 사전 정의 공격 패턴 사용

홈페이지 분석모델
└─ 자동 결과를 사람이 재검증

AI 동적 분석
└─ 머신러닝으로 고정 규칙 보완

크로스 체크
└─ 정적 결과와 동적 결과를 교차 검증

LSTM HAST
└─ SAST·DAST·LSTM 통합

웹사이트 구조화
└─ 페이지와 검사 범위를 구조화

진단 방법 개선
└─ 소스 문맥을 확인한 후 동적 검증

WAVE
└─ 대상 페이지가 룰이 기대한 프로그램인지 콘텐츠 특징으로 먼저 확인
```

## 블랙박스·화이트박스·그레이박스 차이

### 블랙박스

대상의 소스코드와 내부 구조를 보지 않고 외부에서 입력을 보내 출력을 확인한다.

```text
HTTP 요청 전송
    ↓
상태 코드·헤더·본문 수신
    ↓
외부에서 취약점 판단
```

Bitscanner와 Nuclei의 일반 HTTP 검사가 여기에 가깝다.

### 화이트박스

소스코드를 직접 확인하여 위험한 함수와 데이터 흐름을 분석한다.

```text
소스코드
    ↓
사용자 입력의 이동 경로 확인
    ↓
검증되지 않은 위험한 함수 호출 확인
```

웹 애플리케이션 진단 방법 개선 연구의 수동 정적 분석이 여기에 가깝다.

### 그레이박스

테스트 계정, API 문서, CMS 매뉴얼, 일부 소스처럼 내부 정보를 일부 제공받아 검사한다.

홈페이지 분석모델은 CMS 매뉴얼과 소스를 일부 활용하므로 그레이박스 성격을 가진다.

## 탐지 정확도 개선 방식 차이

| 방식 | 장점 | 단점 |
|---|---|---|
| 사전 정의 규칙 | 빠르고 결과를 설명하기 쉬움 | 새로운 공격 탐지에 약함 |
| 수동 검증 | 실제 취약 여부를 자세히 확인 | 시간과 전문가가 필요함 |
| 정적·동적 교차 검증 | 서로의 약점을 보완 | 소스코드와 복잡한 구조 필요 |
| 머신러닝 분류 | 기존에 없던 패턴을 찾을 가능성 | 학습 데이터·일반화·설명 문제가 있음 |
| 사이트 구조화 | 검사 누락과 편향 감소 | 취약점 판정 정확도를 직접 높이지 않음 |
| 콘텐츠 유사도 사전 확인 | 잘못된 프로그램에 룰을 적용하는 문제 감소 | 특징 선택·임계값이 부정확하면 미탐 가능 |

## 실험 수준 차이

```text
실제 도구와 실험 결과가 있는 연구
├─ Bitscanner
├─ AI 기반 동적 분석
├─ 정적·동적 크로스 체크
├─ 홈페이지 웹취약점분석모델
├─ 웹사이트 구조화
├─ 웹 애플리케이션 진단 방법 개선
└─ WAVE

구조만 제안한 연구
└─ LSTM HAST
```

LSTM HAST 논문은 설계 참고자료로는 가치가 있지만, 실제 성능이 우수하다는 근거로 사용하면 안 된다.

## Nuclei와 가장 가까운 논문

### 1순위: Bitscanner

외부 요청, 공격 패턴, 응답 비교 및 보고서 생성 구조가 가장 유사하다.

### 2순위: AI 기반 동적 분석

OWASP ZAP과 AI 시스템을 비교해 기존 규칙 기반 동적 분석을 머신러닝으로 보완한다.

### 3순위: WAVE

취약점 룰과 HTTP 응답을 이용한다는 점에서 Nuclei와 가깝고, 룰 실행 전에 대상 페이지의 콘텐츠 적합성을 확인하여 오탐과 요청 낭비를 줄인다.

### 4순위: 정적·동적 크로스 체크

Nuclei를 다른 분석 도구의 결과를 재검증하는 동적 실행기로 활용할 가능성을 보여준다.

### 코드 생성 AI 웹 점검 논문의 위치

이 논문은 AI가 새로운 취약점을 독립적으로 판단하는 Machine Learning Scanner보다 `전문가가 설명한 반복 작업을 Browser 자동화 코드로 바꾸는 연구`에 가깝다.

```text
웹 Scanner
빠르지만 Pattern 중심

RPA
업무 흐름을 자세히 자동화하지만 작성 시간이 큼

코드 생성 AI
RPA처럼 수행할 절차를 자연어로 설명
    ↓
Selenium 코드 생성
```

Nuclei와 비교할 때는 `Cursor·Continue가 Python 코드를 생성하는 방식`과 `Nuclei -ai가 YAML Template을 생성하고 Engine이 실행하는 방식`의 차이를 중심으로 봐야 한다.

| 비교 항목 | 코드 생성 AI 논문 | Nuclei |
|---|---|---|
| 생성 결과 | Python·Selenium Code | YAML Template |
| 실행 주체 | 생성된 Code와 Browser | Nuclei Engine |
| 로그인·화면 동작 | Selenium으로 직접 작성 | Headless·HTTP Flow 등으로 정의 |
| 판정 구조 | 생성 Code마다 구현 | Matcher·Extractor 재사용 |
| 품질 관리 | 전문가가 오류 수정 | Template 검증·Debug, 추가적인 의미 검증 필요 |
| 대량 실행 | Code 품질과 Browser 비용에 의존 | Concurrency·Rate Limit·Clustering 제공 |

논문이 제시한 `오탐률 0%`와 `약 40% 시간 단축`은 강한 결론으로 인용하기 어렵다. Confusion Matrix와 반복 실험 원자료가 없고, 본문의 20분 대 1시간은 단순 계산하면 약 66.7% 단축이라 결론의 40%와 일치하지 않는다.

## Nuclei와 유사한 오픈소스 비교

### 실행 규칙을 표현하는 방식

| 프로젝트           | 검사 규칙 형식                          | 실제 실행 담당          | 특징                       |
| -------------- | --------------------------------- | ----------------- | ------------------------ |
| Nuclei         | YAML Template·DSL·JavaScript Flow | Nuclei Engine     | 작성이 쉽고 여러 프로토콜 지원        |
| Jaeles         | Signature                         | Jaeles Engine     | Go 기반 서명형 웹 Scanner      |
| Nmap NSE       | Lua Script                        | Nmap와 NSE Library | 조건과 행동을 코드로 자유롭게 구현      |
| Google Tsunami | Java Plugin                       | Tsunami Engine    | 서비스 탐색과 취약점 탐지 Plugin 분리 |
| OpenVAS        | NASL Vulnerability Test           | OpenVAS Scanner   | 대규모 Test Feed와 장기 취약점 관리 |
| Semgrep        | YAML Rule                         | Semgrep Engine    | 실행 중 서버가 아닌 소스코드 검사      |

### Nuclei Template과 Nmap NSE Script 비교

```text
Nuclei Template
├─ id·info
├─ protocol 요청
├─ matcher
└─ extractor

Nmap NSE Script
├─ description·author·categories
├─ hostrule·portrule 등의 실행 규칙
└─ action 함수
```

Nuclei의 Matcher는 응답에서 무엇이 맞아야 하는지를 선언한다. NSE의 `action`은 요청과 판정을 Lua 코드로 직접 작성할 수 있다. NSE가 더 자유로운 대신 작성자가 네트워크 처리와 오류 처리를 더 많이 책임져야 한다.

### Nuclei Template과 Tsunami Plugin 비교

```text
Nuclei
하나의 YAML Template에 요청·판정 조건 기술

Tsunami
서비스 탐색 Plugin
        ↓
취약점 탐지 Plugin
        ↓
확신도 높은 결과
```

Tsunami Plugin은 복잡한 코드를 사용할 수 있지만 개발과 배포 비용이 크다. Nuclei Template은 비교적 읽고 수정하기 쉽고 커뮤니티가 빠르게 새로운 검사를 추가할 수 있다.

## 가장 가까운 비교 대상의 의미

`가장 가깝다`는 하나의 순위로 고정되지 않는다.

```text
Template·Signature 구조 비교
└─ Jaeles

네트워크 Script Engine 비교
└─ Nmap NSE

Plugin 확장 구조 비교
└─ Google Tsunami

취약점 Feed와 관리 구조 비교
└─ OpenVAS

웹 Crawler와 응답 비교
└─ Bitscanner

상태 기반 API 실행 비교
└─ RESTler
```

따라서 보고서에서는 “Nuclei와 가장 비슷하다”라고만 쓰지 말고 어느 부분이 비슷한지 함께 밝혀야 한다.
